# 迷宫竞速 AI：时空寻路与协同截击

## 1. 设计目标

本项目包含两套独立运行的确定性策略：

- `strategy.js`：控制迷宫玩家，优先获取钥匙并成功逃生，同时在风险可控时收集晶片。
- `hunter.js`：控制全部追逐者，预测玩家可能经过的路线，通过联合行动提高接触玩家的机会。

两份脚本均使用标准 JavaScript，不依赖外部文件、第三方库、网络、DOM、存储或额外 Worker。

入口统一为：

```js
function decide(observation) {
  // ...
}


两份脚本不共享变量或 memory。
全部决策基于观察值及上一轮 JSON memory，不使用随机数、系统时间或其他非确定性输入。
设计核心原则：
优先保证规则正确和逃生目标，再优化速度、晶片及追逐效果。

2. strategy.js：走迷宫策略
2.1 总体算法
使用分层规划：
1. BFS 计算静态迷宫最短距离。
2. 根据钥匙状态确定必达目标。
3. 在允许的额外路程内选择晶片目标。
4. 使用时间扩展 A* 搜索实际行动。
5. 对闸门、机关、追逐者及生命风险赋予不同代价。
6. 每个 tick 根据最新观察重新规划。
这种方案结合了 BFS 的低成本全局距离信息和 A* 对动态环境的适应能力。
2.2 地图建模
将二维坐标编码为整数：
id = y * width + x


每个通道格最多连接四个相邻格。
邻接顺序固定为：
right, down, left, up


使用 Int32Array 存储邻接表。
对于固定墙，邻接表中使用 -1 表示不可通行。
BFS 计算的距离忽略周期性闸门，但不忽略固定墙。
因此 BFS 距离是可用于 A* 的静态路径长度估计。
2.3 核心目标优先级
如果玩家没有钥匙：
主要目标 = 钥匙


取得钥匙后：
主要目标 = 出口


在规划过程中，允许选择符合条件的晶片作为临时目标。
这种设计直接对应计分规则：
- 成功逃生贡献 6000 分。
- 成功后的速度最多贡献 2000 分。
- 晶片、探索与生命值合计最多贡献 2000 分。
因此，晶片不应为了少量收益而显著降低逃生概率。
2.4 晶片选择
设：
- P 为当前玩家位置。
- G 为当前主要目标。
- C 为候选晶片。
- d(A,B) 为忽略周期闸门的 BFS 距离。
计算：
direct = d(P,G)

viaCoin = d(P,C) + d(C,G)

detour = viaCoin - direct


detour 是经过晶片所增加的静态最短路程。
根据追逐者数量限制额外路程：
追逐者数量	最大晶片绕路
1	7 格
2	5 格
3	4 格
这些是启发式参数，不是理论最优值。
另外：
- 生命只剩 1 点时，原则上只考虑零绕路晶片。
- 剩余 tick 紧张时，进一步缩小绕路预算。
- 排除距离过远的晶片。
- 降低附近存在追逐者的晶片优先级。
- 对上一轮选择的晶片给予少量持续性奖励，减少目标来回切换。
- 如果长时间没有移动，则取消晶片绕路预算。
晶片候选值采用启发式评分：
value =
    49
    - 7 * detour
    - 0.8 * distanceToCoin
    - dangerPenalty
    + targetInertia


它不是对实际游戏分数的精确预测。
其作用是快速筛选有利于完成主线的晶片。
2.5 时间扩展 A*
普通 A* 只考虑位置。
但游戏中闸门和机关具有周期性，因此必须考虑到达时间。
搜索状态为：
(x, y, relativeTick)


或者编码为：
state = relativeTick * cellCount + cellId


每个状态最多扩展五种动作：
right
down
left
up
wait


每一步对应一个真实游戏 tick。
搜索使用最小堆维护候选状态。
优先级为：
priority = accumulatedCost + 1.07 * bfsDistanceToGoal


1.07 是加权 A* 的启发式系数。
它能够偏向更快的目标推进，但不保证获得数学上的最优路径。
2.6 周期闸门
进入目标格时，判断：
(tick + phase) % period < on


如果闸门关闭，则不能进入。
规划使用未来实际 tick 计算闸门状态，而不是简单沿用当前 closed 布尔值。
同时遵守：
玩家已经位于关闭闸门上时，仍然允许离开该格。
等待也是合法动作。
因此，对于短时间关闭的闸门，A* 可以选择等待开放，而不是进行不必要的长距离绕行。
2.7 机关风险
如果玩家在 tick t 结束时处于激活机关上，且：
t >= invulnerableUntil


则可能受到伤害。
规划中为激活机关添加代价：
生命值	机关危险代价
3 HP	52
2 HP	76
1 HP	175
这些是路径规划的虚拟成本，不是实际扣血量或分数。
当观察状态表明对应未来 tick 仍处于无敌期时，不施加这项伤害代价。
注意：规划器不会完整模拟未来每次受伤之后重新产生的无敌期。
这是为了降低搜索状态数量。
2.8 追逐者危险预测
从每名追逐者的位置执行 BFS，获得其到地图各格的静态距离。
对于当前 tick t 和规划中的第 k 步：
hunterMoves =
    floor((t + k + 1) / hunterEvery)
    - floor(t / hunterEvery)


这个值表示从当前决策开始，到对应结算时刻为止，追逐者最多获得多少次移动机会。
若：
distance(hunter, cell) <= hunterMoves


说明该追逐者在忽略其他动态限制时有可能到达该格。
根据距离与可移动次数的关系，施加不同风险代价。
策略还会：
- 提高低生命值时的危险惩罚。
- 对多个追逐者的风险进行组合。
- 对更远未来的不确定风险进行衰减。
- 利用无敌期减少不必要的危险回避。
- 对长时间停滞的状态降低部分危险惩罚。
追逐者危险预测仅覆盖规划开始后的有限时间窗口。
原因是未来追逐者会根据玩家位置改变方向，单纯把当前位置的可达区域无限扩大，会产生过度保守的判断。
这种危险估计并不是对追逐者真实行动的保证。
2.9 出口的特殊规则
当玩家已经拥有钥匙时：
移动后落在出口
→ 立即成功
→ 不再结算追逐和伤害


因此，规划器在评估直接到达出口的获胜动作时，不施加机关或追逐者伤害代价。
这样可以避免因为出口附近存在追逐者，而错误地放弃已经能够完成的逃生。
2.10 防止永久等待
时间扩展规划有一个常见问题：
如果远期危险模型不完整，搜索器可能认为等待足够久之后，风险就会自动消失。
但真实游戏中的追逐者不会因此消失。
本实现使用两种措施降低这种问题：
1. 为 wait 动作增加额外代价。
2. 根据连续停滞次数进一步提高等待代价。
连续停滞较久时，也会减少部分危险权重并取消晶片绕路。
这能降低保守规划导致无限等待的可能，但不能严格证明所有地图都不会发生停滞或循环。
2.11 搜索预算
为控制单次计算量，限制：
最大规划深度：160 tick

最大扩展状态数：24000


实际深度还受到目标静态距离和剩余 tick 的约束。
如果搜索未找到完整目标路径：
- 首先使用搜索过程中记录的最佳前沿状态。
- 如果没有合适前沿，则执行合法的一步启发式选择。
- 始终返回协议允许的动作。
这是为了兼顾动态规划质量和 200ms 的执行限制。

3. hunter.js：追逐策略
3.1 总体算法
追逐策略不简单地让每名追逐者独立朝玩家当前位置移动。
原因是追逐者移动频率低于玩家。
如果只追逐过去的位置，玩家可能始终保持领先。
因此使用：
玩家未来位置概率预测 + 多追逐者联合行动搜索。
主要步骤：
1. BFS 建立迷宫距离。
2. 推断玩家可能前往的目标。
3. 向前传播 12 步的位置概率分布。
4. 为每名追逐者枚举合法动作。
5. 计算各动作对未来位置的接近程度。
6. 联合评估全部追逐者的动作组合。
7. 选择预计接触机会较大的组合。
3.2 玩家目标推断
根据当前钥匙状态进行预测：
未取得钥匙：倾向于前往钥匙

已经取得钥匙：倾向于前往出口


同时考虑：
- 当前移动方向。
- 最短路径方向。
- 尚未收集的晶片。
- 周期闸门。
- 激活机关。
- 附近追逐者造成的危险。
由于不同参赛者的走迷宫策略可能完全不同，这些规则只表示一种概率预测模型。
不假设对手一定执行最短路径策略。
3.3 概率状态
使用两组概率数组：
withoutKey[cell]
withKey[cell]


它们分别表示预测玩家处于某格且尚未获得钥匙、以及已经获得钥匙的概率质量。
这样可以处理预测期间取得钥匙的情况。
当预测玩家移动到钥匙：
withoutKey → withKey


之后的目标切换为出口。
当已经拥有钥匙的预测玩家到达出口时，该路径的概率质量从后续预测中移除。
这是因为对应世界已经成功结束。
3.4 未来 12 步预测
对于每个可能的位置，枚举：
right
down
left
up
wait


并为合法动作赋予相对权重。
基础规则包括：
行为	倾向
靠近当前目标	高
暂时远离目标	低，但非零
经过晶片	适当提高
进入激活机关	明显降低
进入追逐者可达区域	降低
延续上一次运动方向	适当提高
等待	允许，尤其在通路受阻时
每个位置的动作权重都会归一化。
然后将该位置的概率质量分配给下一时刻的候选位置。
得到：
forecast[1][cell]
forecast[2][cell]
...
forecast[12][cell]


这是确定性计算产生的概率分布，并不使用随机抽样。
因此同样的输入会得到同样的预测结果。
3.5 追逐者候选动作
每名追逐者最多拥有五个候选动作。
枚举时检查：
- 地图固定墙。
- 当前 tick 的关闭闸门。
- 等待动作合法性。
每个候选动作对应一个移动后的格子。
从该格执行 BFS，计算到其他格的静态距离。
如果多名追逐者的候选动作到达同一个格子，则复用该格的 BFS 结果。
3.6 未来截击评价
不只考虑追逐者与玩家当前的位置距离。
还选取未来时间：
2, 4, 7, 11


并分别赋予权重：
0.34, 0.31, 0.22, 0.13


对于每个候选位置，计算到玩家未来概率分布的期望静态距离。
近未来的预测相对更可靠，因此拥有更大权重。
评分中包含：
pressure =
    -5.2 * expectedFutureDistance
    -0.65 * distanceToCurrentPlayer
            * remainingPredictedMass


这个评分鼓励追逐者靠近玩家可能出现的位置，而不是机械地追向当前坐标。
3.7 多追逐者联合搜索
难度最高时只有 3 名追逐者。
每名追逐者最多 5 种动作。
因此联合组合数最多为：
5^3 = 125


这个规模足够小，可以直接枚举。
对每种联合动作组合进行评分。
联合评分考虑三个主要因素：
第一：立即接触概率
计算行动后，至少一名追逐者与玩家可能的新位置重合的概率。
对重复占据同一格的追逐者，不重复计算该格的接触概率。
这符合游戏规则：
同一 tick 内，即使多名追逐者接触玩家，也最多扣除 1 HP。
第二：未来覆盖
计算未来预测位置能否被至少一名追逐者在允许的移动次数内到达。
对于预测时间 s，当前这次移动完成之后还可能获得的行动次数为：
floor((s - 1) / hunterEvery)


使用各追逐者的最小距离评估联合覆盖能力。
第三：减少无意义重叠
多名追逐者完全重叠不一定有利。
因此对重复占据同一格的组合施加少量惩罚。
但不禁止重叠，因为在某些狭窄通道中，重叠可能仍然是合理的行动。
3.8 低生命值目标
若玩家只剩 1 HP，一次成功接触就可能结束世界。
因此，根据玩家 HP 调整立即接触概率的评分权重：
HP = 3：470

HP = 2：620

HP = 1：850


这些数值是搜索启发式权重。
它们不代表真实伤害值。
3.9 同时行动规则
追逐者只使用当前 observation 进行判断。
无法读取玩家本 tick 尚未执行的动作。
因此 hunter.js 返回的是对玩家下一格位置的预测，而不是读取其未来位置。
所有追逐者动作一次性返回：
{
  actions: [
    {id: 0, action: 'left'},
    {id: 1, action: 'down'},
    {id: 2, action: 'wait'}
  ],
  memory: {...}
}


实际追逐者数量由 observation.hunters 决定。
代码不会固定假设始终存在 3 名追逐者。
每个输入中的猎手恰好对应一条输出动作。

4. 状态记忆
两种策略都通过返回 JSON memory 保存少量信息。
4.1 Runner memory
结构：
{
  px: 4,
  py: 7,
  stagnation: 2,
  coin: 139
}


字段：
字段	用途
px	上一次观察到的玩家 x
py	上一次观察到的玩家 y
stagnation	连续观察到位置不变的次数
coin	上次选择的晶片格编号，-1 表示无目标
下一轮利用这些信息：
- 判断是否停滞。
- 增加持续等待的代价。
- 限制停滞期间的晶片绕路。
- 维持短时间内的晶片选择一致性。
不保存完整地图和大规模搜索数组。
因为 observation 每次都会重新提供地图。
4.2 Hunter memory
结构：
{
  px: 12,
  py: 8,
  tick: 35
}


用于记录上一次追逐决策看到的玩家位置和 tick。
下一次追逐决策时：
vx = currentX - previousX

vy = currentY - previousY


将其作为玩家运动方向的弱预测信号。
注意：
由于 hunter.js 不会在每个 tick 被调用，这个位置差通常跨越多个玩家行动。
它不是玩家单步动作。
4.3 独立性
Runner 与 Hunter：
- 不共享 memory。
- 不共享顶层变量。
- 不需要跨 Worker 通信。
- 不需要访问浏览器存储。
即使引擎重建了本地临时搜索数组，也不会影响记忆协议的正确性。

5. 复杂度分析
定义：
V = 地图格子数
E = 通道邻接边数
K = 追逐者数量
C = 剩余晶片数量
H = Runner 时间规划深度
F = Hunter 概率预测深度
M = 全部追逐者的不同候选位置数量


已知约束：
V <= 875
K <= 3
C <= 16
H <= 160
F = 12
M <= 5K


由于每个格子最多有四条邻接边：
E = O(V)


5.1 Runner 时间复杂度
单次 BFS：
O(V + E)


Runner 执行有限次数 BFS，包括：
- 玩家位置 BFS。
- 出口 BFS。
- 钥匙或主目标 BFS。
- 可选晶片目标 BFS。
- 每名追逐者的 BFS。
因此 BFS 总成本为：
O((K + 4) * (V + E))


晶片选择：
O(CK)


危险场构建：
O(13KV)


时间扩展 A*：
最坏情况：

O(HV log(HV))


每个时空状态最多展开五个后继。
实际代码设置：
最大扩展数量 = 24000


因此也受到显式扩展预算约束。
综合主要成本可表示为：
O(
  (K + 4)(V + E)
  + CK
  + 13KV
  + HV log(HV)
)


5.2 Runner 空间复杂度
主要数据：
- 邻接表。
- BFS 距离数组。
- 危险场数组。
- A* 最优代价数组。
- A* 首动作数组。
- 优先队列。
渐近空间复杂度为：
O(HV + KV)


5.3 Hunter 时间复杂度
静态 BFS：
O((M + K + 3)(V + E))


概率传播：
O(FV)


候选动作评分：
O(MV)


更精确地，未来评价还包含固定数量的预测时间帧。
联合组合最多：
5^K


每组组合需要评估有限个未来帧与格子。
其成本上界可写作：
O(5^K * K * V)


因此总体主要成本：
O(
  (M + K + 3)(V + E)
  + FV
  + MV
  + 5^K * K * V
)


由于 K 最大为 3，组合搜索规模较小。
5.4 Hunter 空间复杂度
主要空间来自：
- BFS 距离数组。
- 12 步概率预测。
- 候选位置距离缓存。
- 联合动作组合。
空间复杂度：
O((M + F + K)V)


以上均为算法复杂度分析，不是浏览器执行时间实测结果。

6. 确定性和可复现性
两套策略都不使用：
Math.random()
Date
performance
crypto
网络请求
外部数据


策略不会依赖真实时间、浏览器刷新速度或播放速度。
使用固定的：
- 邻接访问顺序。
- BFS 队列顺序。
- A* 优先队列比较规则。
- 候选动作顺序。
- 联合行动枚举顺序。
相同 observation 与相同 memory 会产生相同输出。
本实现没有随机分支，因此不需要额外的 seed 派生伪随机数生成器。
seed 仍然可以由比赛引擎用于生成地图，但策略本身不使用随机采样。

7. 协议合规性
7.1 strategy.js
每次返回：
{
  action: 'right',
  memory: {
    px: 1,
    py: 1,
    stagnation: 0,
    coin: -1
  }
}


action 必定属于：
up
right
down
left
wait


7.2 hunter.js
每次返回：
{
  actions: [

输出动作数量与输入 hunters 数量一致。
所有 id 均直接使用 observation 中的 id。
不会额外生成 id。
7.3 JSON 安全性
返回 memory 仅包含：
- 普通对象。
- 字符串动作。
- 有限整数。
不会返回：
- BigInt。
- Infinity。
- NaN。
- Map。
- Set。
- TypedArray。
- 函数。
- 循环引用。
内部允许使用 Infinity 表示尚未到达的搜索状态，但不会将其作为输出字段返回。
返回对象规模远小于协议规定的 32768 字符。
7.4 运行环境
实现不包含：
- import 或 export。
- require。
- importScripts。
- fetch。
- WebSocket。
- DOM 操作。
- Worker 创建。
- 动态模块。
- 第三方包。
适用于支持标准现代 JavaScript 的独立 Worker。

8. 已知局限
8.1 Runner 不保证必胜
即使知道全部地图，追逐者仍可能占据重要通道。
玩家只有 3 HP，移动速度也受到每 tick 一格的限制。
存在理论上或实际策略上难以逃生的状态。
8.2 Hunter 风险只是近似
Runner 不知道对手 hunter.js 的真实算法。
危险估计基于静态 BFS 距离和追逐者可移动次数。
真实追逐者可能：
- 主动堵截。
- 等待伏击。
- 分散包围。
- 采取非最短路径行动。
这些行为不一定被 Runner 的短期风险模型准确捕获。
8.3 概率预测不等于玩家真实策略
Hunter 使用目标导向概率传播。
如果玩家故意远离钥匙、采取复杂绕行、长时间等待或执行特殊对抗策略，预测质量可能下降。
8.4 长期规划不完整
Runner 的完整时空规划最多覆盖 160 tick。
Hunter 的未来位置预测覆盖 12 步。
两者都不能完整预测整个比赛。
8.5 静态 BFS 忽略闸门时间
静态 BFS 主要用于距离估计。
Runner 的实际 A* 会处理动态闸门。
但晶片筛选和 Hunter 的部分截击评估没有完整计算时变闸门造成的额外等待。
因此，某些绕路或截击机会可能被错误估价。
8.6 未完整模拟未来生命变化
Runner 的规划没有把未来 HP 和受伤后重新获得的无敌期作为独立搜索状态。
这样可以显著降低状态数量，但无法精确优化所有涉及连续受伤的路线。
8.7 没有形式化胜率保证
A* 使用加权启发式、有限规划深度和扩展数量限制。
Hunter 使用启发式概率模型。
它们都不构成全局最优策略的数学证明。

9. 设计取舍
问题	采用方案	主要理由
全局路线	BFS	简单、确定、速度快
动态路线	时间扩展 A*	能处理周期闸门和机关
A* 性能	加权启发式与预算上限	限制单次计算规模
晶片收集	有限绕路	不让次要分数凌驾于逃生
追逐者风险	短期可达性估计	不要求知道对手代码
Hunter 目标预测	概率传播	容许玩家不走唯一最短路
多 Hunter 行动	完整小规模联合枚举	最多 125 组，易于控制
状态记忆	极小 JSON 对象	低开销、可复现
随机性	不使用	避免重赛产生额外差异
外部依赖	无	满足沙箱限制

10. 测试与性能声明
上述实现按照题目给出的规则和输入输出协议设计。
本文未声称已经在官方比赛引擎、全部随机地图、全部难度或所有对手策略下完成实测。
不提供未经正式评估的：
- 通关率。
- 平均得分。
- 排名。
- 平均决策耗时。
- 最坏决策耗时。
- 胜率百分比。
代码通过搜索深度、状态扩展数量和有限组合枚举约束计算规模，但具体是否始终满足某个浏览器中的 200ms 限制，仍取决于实际执行环境。
可复现的正式评估应使用固定地图种子、难度、完整参赛名单和顺序，并分别记录 runner 得分、结束状态、结束 tick、生命值及每次决策耗时。
11. 总结
Runner 的核心思想是：
先确保钥匙与出口的主线，利用时间扩展寻路规避即时危险，只在成本可控时收集晶片。
Hunter 的核心思想是：
预测玩家未来位置，而不只追逐当前位置；将多名追逐者作为一个团队联合选择动作，提高即时接触与未来截击覆盖。
两套策略都以确定性、有限计算量、协议正确性和可复现性为基础，并明确保留对未知对手和复杂动态环境的建模局限。
