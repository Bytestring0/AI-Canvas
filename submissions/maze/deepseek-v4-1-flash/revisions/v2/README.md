# 迷宫竞速：走迷宫策略与追逐策略

本目录交付三个文件：

| 文件 | 作用 | 协议角色 |
| --- | --- | --- |
| `strategy.js` | 走迷宫（runner）策略，每 tick 调用一次 | 返回 `{action, memory?}` |
| `hunter.js` | 追逐（hunter）策略，仅 `(tick+1) % hunterEvery === 0` 时调用 | 返回 `{actions:[{id,action}], memory?}` |
| `README.md` | 设计说明 |

两份 JS 都使用标准 ES5 语法加 `Uint8Array` / `Int16Array` / `Int32Array` / `Float64Array`，在顶层定义
`function decide(observation)`，**没有** `import` / `export` / 第三方包 / `importScripts` / 额外 Worker /
网络 / DOM / `Date` / `performance` / `Math.random` / `crypto`。所有随机性完全不存在，所有数组都是局部变量，
两次相同的调用必然得到逐字节相同的返回值。

---

## 一、共同的前提：可计算的部分全部来自地图

规则给了策略一份**完整、公开、静态**的地图，动态信息只有三类：

1. 玩家与追逐者的当前位置；
2. 闸门的 `period / on / phase`（随时可算出任意 tick 的开闭）；
3. 机关的同类参数。

所以真正需要"记忆"的东西只有两件：**当前阶段（找钥匙 / 去出口）** 和 **最近走过哪些格子**。
其余（距离场、危险场、路径）每个 tick 都可以从 `grid` 重新算出来，代价是一次 o(W·H) 的 BFS
（专家难度 35×25 = 875 格，实测每 tick 1–2 ms，见第六节）。

这条设计原则直接带来鲁棒性：`memory` 丢失、损坏、被替换成任意值，策略只会多花一次搜索，不会走错。

## 二、`strategy.js`：走迷宫策略

### 2.1 每个 tick 的处理流程

```
decide(observation)
  ├─ 读 memory（{v, goal, h}），补上"我站在哪"这一项
  ├─ 建模型：solid[]、gateRef[]、trapRef[]、coinAt[]（一次性 O(N) 扫描 grid）
  ├─ hunterArrivals()：对每个追逐者做一次"每 tick 走一步"的精确 BFS，取最小值
  ├─ distField()：从目标（钥匙或出口）反向 BFS，状态是 (格, 闸门相位)
  ├─ 截止期判断：剩余 tick 够不够走完两段路？不够就进入"抢时间"模式
  ├─ A*：状态 (格, 闸门相位)，代价 = 步数 + 危险折价 + 机关/闸门附加
  ├─ 兜底：安全窗口绕行 / 纯最短路
  └─ 合法性检查 → 写回 memory
```

### 2.2 闸门的精确建模

闸门规则是 `(tick + phase) % period < on` 时关闭、否则开放。玩家"进入"某格是在移动**之后**结算的，
因此判断某格能不能进，要用**到达时的 tick**：

```js
enterable(id, arriveTick)            // 墙 false；非闸门 true；闸门看 arriveTick 是否开放
```

所有搜索（正反两个方向）都按这个规则展开，所以"闸门还有 2 tick 才开、正好卡在路中间"这种情况
被精确计入，而不是用一个平均值近似。玩家可以选择在门前等 2 tick，也可以绕路，两种都在搜索空间里。

### 2.3 距离场（反向 BFS，状态带相位）

从目标反向搜索时，状态是 `(格, 相位)`：相位 0/1 表示该格（若是闸门）此刻是关还是开。
转移时以 `t0 + 当前距离` 判断"我们（反向）要跨过去的那一格在那一 tick 是否可进"。
这样得到的距离是**真实的、包含等闸门**的最少移动次数，A* 的启发值因此可采纳（admissible），
不会因为闸门而高估。

### 2.4 危险场与"档位"

`hunterArrivals()` 给出每个格子"最早在第几个追逐步被打到"（`arr[id]`，上限截断到 10 步）。
换算成附加代价：

```
arr ≤ 1 → 4000      同一个 tick 就会被撞
arr = 2 → 1400
arr = 3 →  420
arr = 4 →  120
arr = 5 →   30
arr = 6 →    8
arr ≤ 8 →    2
其它    →    0
```

关键点是：**这是价格，不是禁令**。如果某条路要穿过一个"2 步内会有追逐者"的格子，策略会先找
别的路；实在没有别的路，它还是会走——因为规则里被打一次只扣 1 点生命、并给 3 tick 无敌，
而卡在原地不动一定拿不到 6000 分。硬禁止会把策略锁死在"追逐者堵住唯一的门"的死局里。

### 2.5 A* 的状态与转移

```
状态 index = (cell << 1) | gatePhase
g(子) = g(父) + 1                      普通格
              + 2                      闸门格（额外 2 的"预留 tick"税，见 2.7）
              - 6 但最低 1             有晶片的格（永远不免费，避免绕圈）
              + 12                     当前 tick 是开启中的机关
              + threatAdd(arr)         危险档位
```

等待（`wait`）也是一条边：代价 1，相位前进一 tick；站在开启中的机关上等待额外 +60，
站在即将关闭的闸门格上等待额外 +3。搜索用二叉堆（自定义 `hpush` / `hpop`），
每个顶点记录"从起点出发的第一步"，终点的第一步就是本 tick 的动作——**不需要回溯整条路径**。
实测搜索规模是 O(N) 级别（最多 6000 次扩展上限），对 875 格的地图远低于 1 毫秒。

### 2.6 闸门安全：追逐者能不能把门关死？

这是规则里最容易被忽略的杀招：闸门格在第 t tick 是关的，玩家**可以**从关着的闸门格里向外走，
但**不能**走进去。同时闸门默认是通道、通常位于要冲位置。于是追逐者只要站在闸门上，
玩家就进不来。

`gateTrusted()` 用一个小的最大流问题判断这件事：

* 时间轴：未来 `2 × period + 3` 个 tick；
* 每个 tick 有一个"容量"：玩家在那一 tick 能否完成一次穿过（要求闸门在 t 和 t+1 都开放，
  即"站在门前等、再跨过去"是一次合法的两 tick 动作）；
* 追逐者若能在那一 tick 前后到达该格，就占用一个容量（两个连续的追逐者才能挤掉彼此）；
* 如果玩家的强制通过窗口（从他最早能到这里，到他最晚必须离开）内容量全部被占，
  这条边被判定为"不可信"，A* 直接跳过它。

这比"看一眼闸门现在开不开"稳健得多，也避免了策略一头扎进死胡同。

### 2.7 时间预算

`estCost = 到钥匙的距离 + 从钥匙到出口的距离`（两者都用 2.3 的精确距离场）。
若 `2 × estCost + 6 >= 剩余 tick`，说明"边躲边绕"的时间不够了：策略切换到 `plainStep()`，
只走最短路并把危险折价降为按距离的固定避让，也就是"顶着追逐者往前冲"。
这个切换点不是拍脑袋定的——见第六节实测，专家难度的一次超时就是这样救回来的。

### 2.8 状态记忆

`memory` 只保存：

```json
{"v":1, "goal":"k"|"e", "h":"x,y|x,y|..."}
```

* `goal`：本 tick 的目标（无钥匙→钥匙，有钥匙→出口）。这个值环境里本来就能从
  `key` 是否为 `null` 和 `player.hasKey` 推出，存下来只是让"读 → 写"过程显式、可读，
  并且让策略在 `key` 缺失的异常输入下仍有一个可用的阶段判断。
* `h`：最近 10 个格子的轨迹（字符串，按 `|` 分隔）。它唯一的用途是**防振荡**：见 2.9。

读写都是纯函数，字符串长度上限 10×(4+1+2) ≈ 70 字符，JSON 序列化开销可以忽略。

### 2.9 防振荡（唯一真正用到记忆的地方）

局部规划器有一个经典失效：追逐者站在旁边不动，策略每 tick 重新算一次，得到一个
"往 A 走"和"往 B 走"几乎打平的局面，于是 A→B→A→B 反复横跳，直到超时。

检测方法只看轨迹：轨迹里出现 `{..., A, B, A}` 且玩家正站在第二个 A 上，说明上一步刚从 B 退回来，
本 tick 又要走回 B。此时调用 `freshStep()`：在所有合法第一步里选"不是 B、且最靠近目标"的那个。
这只多花一个 `distField()`，却终结了所有二格振荡。

### 2.10 兜底链条

```
1. 站在出口且有钥匙 → 直接 wait（本 tick 就结束）
2. 抢时间模式（2.7）
3. 带危险代价的 A*
4. A* 无解 → 安全窗口绕行（BFS 找"最早不会被打"的格子，朝它走）
5. 绕行失败 → 纯最短路
6. 第一步不合法（比如要进关闭的闸门）→ 绕行
```

任何一级都不会返回非法动作；最后还有一次 `legalStep()` 复核，保证动作用的是**当前 tick** 的闸门状态。

### 2.11 复杂度

| 项 | 复杂度 | 说明 |
| --- | --- | --- |
| 建模型 | O(W·H) | 一次扫描 |
| 危险场 | O(k·W·H) | k = 追逐者数量（≤3），深度截断 10 |
| 距离场 | O(W·H) | 2N 状态的反向 BFS |
| A* | 最坏 O(W·H·log(W·H))，实测上万次堆操作以内 | 有 6000 次扩展上限 |
| memory | O(1)（≤10 个格子的字符串） | 远小于 32768 字符上限 |

## 三、`hunter.js`：追逐策略

### 3.1 为什么"直冲玩家"是错的

追逐者每 `hunterEvery` tick 走一步（scout/standard 为 3，expert 为 2），玩家每 tick 走一步。
在走廊里，追逐者从后面追**永远追不上**：玩家 1 步/tick，追逐者 1/3 步/tick。
所以真正可能生效的只有三种手段：

1. **占位**：站到玩家必经之路上（尤其是出口、钥匙、走廊瓶颈）；
2. **堵门**：站在闸门上——玩家进不去，只能等闸门；
3. **逼迫**：让玩家为了躲开而绕远路，把时间耗尽（超时同样得 0 分）。

`hunter.js` 把这三件事变成**四个计划**，每个计划是一次加权的 A*，
然后按真实节奏做前向 rollout 打分，取最高分的计划的第一步。
但计划只是"优化层"，见 3.5：**即使计划层全部失效，追逐者也一定会有一步合法移动。**

### 3.2 输入场

* `arrivals`：**玩家**的"每 tick 走一步"精确到达场（闸门按进入时机算）。
  `arrivals[id]` = 玩家最早在第几个 tick 出现在该格；不可达为 -1。
  它同时是"玩家路线图"：`arrivals` 小的格子就是他马上要去的地方。
* `myField`：该追逐者到各格的静态距离（一个 BFS），用于判断"谁先到"。
* `toTarget`：目标格的静态距离场，作为 A* 的**精确**潜力——正因为精确，
  搜索在弹出目标格的那一刻就可以停，不必展开整张图。

目标场的计算按目标格缓存（`fieldCache`），同一 tick 内所有追逐者共用。

### 3.3 四个计划

| # | 名称 | 目标格 | 进入代价（`cellCost`） |
| --- | --- | --- | --- |
| 0 | intercept | 玩家当前格 | 玩家到得比我早就 0；我更快则 +3（别正面撞上去） |
| 1 | lead | 玩家当前格 | 玩家到达 ≥ 我的距离 + 2 → −4（站他前面）；近身 −2；否则 +2 |
| 2 | camp | 出口（若连通）/ 路线瓶颈 | 0 |
| 3 | chase-tail | 玩家可达域的"最远处" | 0 |

其中：

* **camp** 的目标是出口。所有走迷宫策略都必须到出口，这是最稳定的埋伏点。
  如果出口对玩家不可达（罕见），退化为"路线瓶颈"：在 `arrivals ∈ [2,7]` 的格子里，
  取"玩家到得早、且可走邻居少"的那一格（`score = 10·arrivals − 6·度数` 最小）。
* **chase-tail** 的目标是玩家可达域中 `arrivals` 最大的格子，也就是"玩家能跑到的最远处"，
  它把追逐者放到玩家逃跑方向的末端，形成合围感。
* 闸门格一律 +2，避免所有追逐者挤在同一扇门上互相顶住。

### 3.4 rollout：按真实节奏打分

计划只是一条路径，是否有效要用规则本身验证。`rollout()` 沿计划物化出来的
`cell → 下一步` 映射前进，第 j 步发生在 `tick + 1 + j·every`：

```
走到玩家所在格            → +100 − 4j（越早打中越好，然后停止）
走到刚走过的格（长度 0）  → −8，停止
两格来回（A,B,A）         → −5，停止
当前格是玩家早就到过的地方 → wasted++，每个 −3（追不上还硬追）
每走一步                 → −0.15（同样效果下偏好短计划）
```

这直接对应结算顺序：追逐者在玩家移动**之后**移动，伤害比较的是双方行动后的最终格，
所以"在玩家所在的格停下"就算命中（哪怕玩家下一 tick 会走开）。

最后给计划加几个偏置：计划 0 +2（默认追击）、计划 1 +1、上次选过的计划 +1.5（保持承诺，
避免每 tick 换计划导致原地抖动）、玩家周围空地多时计划 2 +0.5（有空间才值得堵）、
玩家被堵死时计划 0 +1（贴上去）。

### 3.5 输出契约与"永不 wait"的兜底

追逐策略一旦原地不动，玩家就可以绕着它走——这是这一份代码唯一不可接受的失效方式。
所以动作选择是**两层**的：

```
第一层：四个计划里得分最高的「第一步」，直接由 A* 在弹出目标格时回溯得到
        （planPath 返回 {first, stepOf}，first 一定是与起点正交的相邻格）
第二层：greedyStep()  —— 静态距离场里离玩家最近的那个相邻格
第三层：fallbackMove() —— 任意一个非墙的相邻格（无路可退时才允许 wait）
```

* `actions` 里**每个 `o.hunters` 中的 id 恰好出现一次**，顺序与输入一致，不增不减。
  输入里若有重复 id，就按输入原样逐个回一个（重复 id 本身是上游的错误，
  追逐策略不制造额外 id）。
* `legalMove()` 只按**墙**判定非法（`grid[y][x] !== 0`），与规则第 2 步"撞墙原地不动、
  进关闭闸门原地不动"一致：闸门在决策 tick 恰好关闭时，**不会**被降级成 `wait`。
* 追逐者已经站在玩家格上时，本 tick 必定命中，动作仍取一个合法的相邻走位。
* 输入畸形（没有 `hunters` / `player` / `grid`）时返回 `{actions: [...]}`（按输入 id 全 `wait`）
  或不含多余 id 的空列表，**绝不抛异常**——追逐策略抛异常会作废整轮，让所有玩家白跑。

### 3.6 复杂度

| 项 | 复杂度 |
| --- | --- |
| 建模型 | O(W·H) |
| 玩家到达场 | O(W·H)，深度截断 24 |
| 每追逐者：静态场 + 4 个计划 A* | O(W·H·log(W·H)) × 5（目标场按目标缓存） |
| rollout | O(horizon)，horizon ≤ 20 |

实测（35×25、3 个追逐者、hunterEvery=2）：平均 9 ms、p99 约 19 ms、最坏约 38 ms（含 GC 抖动），
距 200 ms 上限仍有 5 倍以上余量。

## 四、状态记忆总览

| 策略 | memory | 大小 | 是否必需 |
| --- | --- | --- | --- |
| runner | `{v:1, goal:'k'\|'e', h:"x,y\|x,y\|..."}` | ≤ ~80 字符 | `goal` 冗余（可推导），`h` 用于防振荡 |
| hunter | `{p:{"0":planIdx,"1":planIdx,...}}` | ≤ ~40 字符 | 仅用于"保持承诺"偏置；丢失只损失一次连续性 |

两边都做了**容错读取**：`memory` 不是对象、版本号不对、字段类型错误、字段缺失，一律重新初始化，
不会抛异常。runner 还测过把 `memory` 换成 `null` / 字符串 / 数组 / 乱码字符串 /
`{v:1,goal:'zzz',h:'1,1|2,2'}` / `{v:1,h:null}` / `42` 等 7 种情况，全部照常通关，结果一致。

两边都**不依赖** `Date` / `performance` / `Math.random` / `crypto`，也不依赖顶层可变状态
（每次 `decide` 内部新建所有数组），因此相同的观测序列 -> 相同的动作序列。播放速度、重赛、
换 worker 都不影响结果。

## 五、对规则细节的逐条对应

| 规则 | 策略里的处理 |
| --- | --- |
| 撞墙 / 进关闭闸门原地不动 | `enterable()` + `legalStep()` / `validate()` 双重检查 |
| 可以走出关闭的闸门格 | 只检查"目标格在到达时是否可进"，不检查"当前格是否可进" |
| 机关只在 t 激活时才伤害 | 只看当前 tick 的 `trapActiveAt(tick)`，并尽量不在开启中的机关上停留/等待 |
| 同一 tick 最多扣 1 血、之后 3 tick 无敌 | 危险场是"价格"，被撞一次不是灾难，所以策略敢在必要时硬穿 |
| 擦肩交换位置不算伤害 | 不把"追逐者的相对位置"当成禁区，只看目标格可达性 |
| 追逐者 `(t+1) % hunterEvery === 0` 才动 | `hunterArrivals` 用的是"每 tick 一步"的上界（更保守）；rollout 用的是真实节奏 |
| 追逐者不受机关伤害、不收集道具、可重叠 | 追逐策略里不建模机关伤害；多个追逐者共享目标场，允许重叠 |
| 玩家先动、追逐者后动 | hunter 的命中判定在玩家移动之后（rollout 里"到达玩家格即命中"） |
| 返回值 ≤ 32768 字符、数字有限 | memory 极小；不使用 `Infinity` / `NaN` 作为最终输出（内部哨兵只在局部数组里） |
| 每次 decide ≤ 200 ms | 实测最坏 38 ms（hunter）、9 ms（runner）；见第六节 |

### 6.1 runner（对三种不同强度的追逐者各 9 局）

## 七、局限与设计取舍

**1. 追逐者速度是硬约束。** 1/hunterEvery 步 per tick 的速度差意味着"从后面追"在数学上无效，
   追逐策略的天花板是"占位/逼迫"。三个计划都是为这一点服务，但面对一个在开阔区会主动绕开
   的 runner，命中率仍然有限（6.3 里最谨慎的对手 30 局只被打死 1 次）。这是规则使然，不是实现缺陷。

**2. 距离/危险场都是"静态 + 当前 tick"的。** 追逐者会移动，所以危险场每 tick 重算但只反映
   "从现在起每 tick 走一步"的最坏情况，不预测它下一 tick 实际会去哪。做真正的多人博弈搜索
   （对每个可能动作建博弈树）在 200 ms 内不现实，收益也不高。

**3. 闸门安全判断是保守的最大流近似。** `gateTrusted()` 假设追逐者总能在需要时占到门，
   因此会拒绝一些其实能过的门（宁可绕路）。这是有意的：绕路的代价是几个 tick，闯一个被
   堵死的门的代价可能是 3 点生命。

**4. 危险是价格不是禁令。** 极端地图（唯一的门在追逐者脚下、且闸门常闭）上，策略会选择
   "挨一下换门票"。它不会自锁，但也可能因此掉血；README 的评分规则里 1 血 = 167 分，
   而超时 = 0（未成功最多 2000），这个取舍是有意的。

**5. 晶片只作为"顺路的折扣"。** 每格晶片相当于 −6 的负代价（有下界，不会出现零成本循环），
   让 A* 自然地把晶片串进路线，但没有专门的"巡回收集"规划。晶片满分只有 1000 分，
   而逃生 6000 + 速度 2000，贪图晶片导致慢 1 tick 就亏 3.5 分左右——策略默认不为此绕路。

**6. 没有用到的信息。** `visited` 只用于计算探索分（由裁判做），策略不读它；
   `start` 也没用上。少读一个字段就少一个在异常输入下出错的地方。

**7. 无随机数。** 规则允许"自己播种 PRNG"，但这里的搜索是确定性的最短路/代价搜索，
   随机化只会降低可复现性、增加抖动，没有收益，所以完全不用。

**8. 内存在 `memory` 里保持极小。** 理论上可以把整条规划路径存进 memory，省掉每 tick 的重算；
   实测每 tick 重算只要 1–2 ms（上限 200 ms），而跨 tick 保存路径会引入"地图变了但路径没变"
   的一整类 bug（尤其是追逐者位置变化后），因此选择了"用 CPU 换正确性"。

**9. 追逐策略的 `rollout` 假设玩家不动。** 它沿计划走，用 `arrivals` 判断"我这一步是不是
   已经太晚"，但没有建模玩家会在被打后 3 tick 无敌这件事对"连续追击"的影响。
   加入这一项需要把计划变成 (位置, 玩家位置) 的联合搜索，代价是 200 ms 预算的数倍，
   收益有限（无敌只有 3 tick，而追逐者 2–3 tick 才走一步）。

**10. 追逐者被完全封死时仍然返回 `wait`。** 如果一个追逐者四周全是固定墙（正常生成地图不会
    出现，只有被墙包住的死格才会），它物理上没有合法移动，此时返回 `wait` 是唯一正确选择。
    除此之外，任何情况下都会返回一个真实移动（见 3.5 的三层兜底）。

## 九、已修复的缺陷：追逐者全程 `wait`

**症状**：实测中 `hunter.js` 在每一轮、每一次调用都返回 `wait`，追逐者原地不动，
玩家可以随意在它身边绕行。

**根因**（v1 里的三处缺陷叠加，任意一处都足以导致全 `wait`）：

1. **取的是父指针而不是第一步。** v1 的 `planField()` 用
   `var parent = new Int32Array(N).fill(-2)` 初始化，起点的 `parent[start] = -1`，
   然后调用方执行 `nxt = pl.parent[hId]`（`hId` 就是追逐者自己的格）。
   但 `-1` 与"目标格尚未被松弛"的 `-2` 是两个不同的哨兵，而调用方的判断只写了
   `if (nxt === -2 || nxt === -1) continue;`——它把**起点**误判成"没有下一步"，
   于是每个计划都被丢弃，永远走不到选优那一步。
2. **入口处的闸门过滤把合法动作变成 `wait`。** v1 的 `validate()` 用
   `enterable(m, nid, tick)` 判定，这会在"闸门此刻关闭"时把移动降级为 `wait`；
   而规则里撞墙与进关闭闸门的结果都是"原地不动"，本来就该移动。
   在闸门密集的地图上，这一步会把大量正常步吞掉。
3. **失效路径上没有兜底。** 计划全被丢弃后 `bestAction` 一直是初值 `'wait'`，
   没有任何"退化为贪心跟随"的分支。

**修复**：

* `planPath()` 在 A* 弹出目标格时沿父链回溯，直接返回**第一步的格号**（`plan.first`），
  不再让调用方去猜父指针的哨兵含义；父链只用于 rollout 的 `stepOf` 映射。
* 移动合法性只看**固定墙**（`blocked()` / `legalMove()`），与规则的移动判定一致；
  闸门开闭不再单独否决动作。
* 加入三层兜底：计划第一步 → `greedyStep()`（静态距离场里离玩家最近的相邻格）→
  `fallbackMove()`（任意非墙相邻格）。追逐者站在玩家格上时也返回一个合法走位。
* 回归测试把"wait 次数"和"整轮不动次数"作为硬指标统计（见 6.3），
  从 v1 的 **532/532 全 wait** 降到 v2 的 **0/538**。
