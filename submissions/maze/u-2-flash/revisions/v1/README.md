# 迷宫竞速：strategy.js 与 hunter.js 设计说明

本文档说明两份策略的实现思路、状态记忆、复杂度、局限性与设计取舍。两份文件均为纯标准 JavaScript，无任何 import/export、第三方依赖或非确定性输入；同一地图、同一种子与名单下结果可复现。

---

## 1. 走迷宫策略（strategy.js）

### 1.1 目标选择

每个 tick 先确定当前目标：

- 未拿到钥匙 → 目标是**钥匙**（`o.key`）；
- 已拿到钥匙 → 目标是**出口**（`o.exit`）；
- 已拿钥匙且仍有晶片时，计算每个未收集晶片的绕路代价：
detour = BFS(玩家→晶片) + BFS(晶片→出口) - BFS(玩家→出口)

复制

若最小 `detour ≤ 8`，则把该晶片设为临时目标（提交后保持目标稳定，避免来回切换）。晶片分值高、绕路成本低，顺路收集是正收益；钥匙未拿到前不主动绕路，保证逃生优先。

### 1.2 时间依赖的 A* 路径规划

核心是 `planPath`：在 `(格子, 已走步数)` 状态空间上做 A* 搜索。

- 每一步代价为 `1`（时间流逝）；
- 落在**激活机关**上额外加 `TRAP_PENALTY=25`；
- 根据“未来某时刻追逐者最多能移动几次”计算**猎人风险惩罚**：从每个猎人当前位置做闸门全开的 BFS 得到可达距离上界，若玩家到达某格前猎人可能赶到，则按危险等级累加惩罚（上限 24）；
- 闸门在到达 tick 关闭时不可进入；允许 `wait`，从而可以等待闸门开启或机关熄灭；
- 启发函数为“忽略闸门到目标的 BFS 步数”，是可行下界，保证 A* 最优性；
- 若目标太远或预算（45000 次扩展）不足，返回当前已找到的“最接近目标”的路径前缀，实现动态重规划。

关键修正：`decide` 收到的 tick 是回合开始时刻，本回合移动的闸门/机关状态由**当前 tick** 决定，因此路径中第 k 步使用 `startTick + k` 时刻的状态判断；出口格视为胜利格，不叠加机关/猎人惩罚。

### 1.3 路径缓存与定期重规划

路径以扁平数组 `[x0,y0,x1,y1,...]` 存入 `memory`，每个 tick 只取首步并消费，避免每 tick 都跑完整 A*。以下情况触发重规划：

- 目标变化（拿到钥匙、晶片被收集、绕路目标切换）；
- 缓存路径下一步非法（墙/关闭闸门）或会被猎人立刻抓到；
- 每 `REPLAN_INTERVAL=10` tick 强制刷新一次，让路径适应猎人位置变化。

### 1.4 猎人安全覆盖

- 每个 tick 计算从每个猎人出发、以当前关闭闸门为墙的 BFS 距离图；
- 对计划落点计算“本 tick 结束后距最近猎人的有效距离”（猎人 tick 时减 1，因为猎人会移动一步）；
- 若有效距离 ≤ 1 且不在无敌期，则调用 `chooseEvade`：在合法移动中综合「离猎人更远、避开激活机关、靠近目标、确定性平局」打分，选最优；
- 无敌期（`invulnerableUntil`）内跳过回避，利用无敌窗口穿过猎人；
- 有钥匙且一步可到出口时直接走出口，无视猎人。

### 1.5 兜底逻辑

- A* 无结果时用贪心回退：朝目标 BFS 距离最小的合法方向走；
- 位置连续 `STUCK_LIMIT=10` tick 不变时，用 seed+tick 哈希确定性强制移动，避免死循环。

## 2. 追逐策略（hunter.js）

### 2.1 玩家下一步预测

`predictPlayerNext` 模拟玩家的贪心决策：

- 以玩家目标（钥匙或出口）做 BFS 距离图；
- 对玩家每个合法移动（含 wait）打分：距离目标越近越好，踩中本 tick 激活机关 +30，可能被猎人抓到 +100（本 tick 会被抓）或 +8（距离 ≤ 2）；
- 取分最低的移动作为玩家预测落点。

### 2.2 猎人移动

`stepToward` 以目标格为源做 BFS（当前 tick 关闭的闸门视为墙），让猎人走向距离目标最近且合法的邻居。BFS 每猎人每次调用仅 O(W×H)，开销极小。

### 2.3 多猎人协同

按“到玩家预测落点的 BFS 距离”给猎人排序，分工不同：

- **最近的主追猎人**：若距离预测点 ≤ 1 或距离玩家 ≤ 3，直接扑向预测落点（尝试立刻抓到）；否则瞄准玩家在**下一次猎人移动时刻**的位置（`playerPath[E-1]`），即提前拦截；
- **其余猎人**：分别瞄准玩家路径上更靠前的拦截点（第 `(rank+1)*E - 1` 步），从前方切断玩家通往钥匙/出口的路线，形成包围。

该策略不依赖随机数，同一观测必然返回同一组动作。

## 3. 状态记忆

| 文件 | memory 内容 | 说明 |
| --- | --- | --- |
| strategy.js | `{path, tx, ty, tt, planTick, lastX, lastY, stuck}` | `path` 为扁平坐标数组（≤220 步）；`tx/ty/tt` 是当前路径目标；`planTick` 用于定期重规划；`lastX/lastY/stuck` 用于卡死检测。全部为 JSON 安全的小整数/字符串。 |
| hunter.js | `null` | 猎人观测已包含完整地图与玩家位置，无需跨 tick 记忆。 |

玩家与猎人的 memory 完全隔离，互不共享。

## 4. 复杂度

设地图格数 `N = width × height`（最大 35×25=875），猎人数量 `H ≤ 3`，规划步数上限 `S ≤ 220`。

- **BFS 距离图**：每次 `O(N)`，空间 `O(N)`；每个 tick 最多调用约 `H+3` 次。
- **A\* 路径规划**：最坏状态数 `O(N·S)`，堆操作 `O(log(N·S))`；通过预算（45000 次扩展）和启发式剪枝限制实际开销，单次规划在最坏情况下也在几十毫秒量级，远低于 200ms 上限。
- **猎人 decide**：`O(H·N + H·N log H)`，实际约 9 次 BFS，恒为轻量。

两份文件均远小于 100000 字节；返回 JSON 大小主要由路径数组决定（约几百到几千字符），远低于 32768 字符上限。

## 5. 局限性与设计取舍

- **猎人预测是贪心的**：`predictPlayerNext` 假设玩家每步“朝目标走并局部避障”，但实际玩家（尤其是本仓库的 strategy.js）使用全局 A* 并带路径缓存，预测可能偏差；拦截点因此只是启发式，不是最优博弈。
- **A\* 做了简化**：以 `(格子, 步数)` 为状态、按代价剪枝，可能漏掉“晚到但更优”的时序路径；规划视界截断为 220 步，超长路径靠动态重规划拼接，不是全局最优。
- **猎人风险是软惩罚**：`hunterDanger` 基于“猎人直奔该格”的最坏可达性上界，可能高估危险导致轻微绕路；也可能因猎人实际路线不同而低估。安全覆盖只检查“本 tick 是否会被抓”，对 2~3 步后的合围依赖定期重规划来缓解。
- **晶片绕路阈值固定**：`COIN_DETOUR_MAX=8` 是经验值，未针对不同 maxTicks 自适应；在极短时限下绕路收益可能变小。
- **卡死阈值**：`STUCK_LIMIT=10` 的强制移动可能在极端闸门等待场景下打断合理等待，但 10 tick 已超过闸门最长关闭期（2 tick）与周期（6–8），实际影响很小。
- **未做实测**：本文档不包含模拟成绩或胜率数据；所有参数均为设计推断，可通过同图重赛进一步调优。
