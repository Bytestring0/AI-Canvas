# 迷宫竞速：走迷宫 / 追逐 双策略说明

本目录交付三个文件：

| 文件          | 角色             | 对外接口                                                                |
| ------------- | ---------------- | ----------------------------------------------------------------------- |
| `strategy.js` | 走迷宫（runner） | 顶层 `function decide(observation)` → `{action, memory}`                |
| `hunter.js`   | 追逐者（hunter） | 顶层 `function decide(observation)` → `{actions:[{id,action}], memory}` |
| `README.md`   | 本文档           | —                                                                       |

两份 JS 都是**纯同步**脚本：不 import / export、不用第三方包、不读文件、不联网、不碰 DOM、
不用 `Date` / `performance` / `Math.random` / `crypto`，也不创建 Worker。
所有随机性都来自 observation 本身（`seed`、地图、机关/闸门相位），因此同一地图 + 同一难度 +
同一次调用序列必然复现同样的决策序列。

---

## 0. 结算顺序里最关键的三条事实

这两份策略的设计几乎全部建立在这三条规则上，先摆出来，后面所有取舍都好解释。

1. **成功判定先于伤害判定。**
   协议第 3 步先判「有钥匙且落在出口 → 成功」，第 5 步才判伤害。
   所以**站在出口格子上的猎手根本吓不到玩家**——玩家一进出口格就结算成功了，血都不会掉。
   推论：玩家**绝不该**为了躲出口上的猎手而绕路；猎手**也绝不该**把宝贵的站位浪费在出口格上。
   （`hunter.js` 明确把目标格从候选站位里剔除。）

2. **玩家先动，猎手后动，且猎手看到的是玩家"动之前"的位置。**
   猎手的决策基于 tick 开始时的玩家位置，玩家这一拍要去哪里，猎手并不知道。
   所以：
   - 玩家**贴着猎手换位**（我走进它的格子、它走进我原来的格子）是规则明确豁免的，**不掉血**；
   - 但玩家**停在原地**而猎手移动过来 → 同格 → 掉血。
   → 结论：**"站着不动"在猎手旁边几乎等于送死，而"主动迎上去换位"往往是免费的。**

3. **猎手比玩家慢。**
   猎手每 `hunterEvery`（2~3）个 tick 才动一格，玩家每 tick 动一格。
   猎手的移动速度只有玩家的 1/2 ~ 1/3，所以"跟在屁股后面追"在几何上永远追不上。
   → 猎手唯一的价值是**出现在玩家前方**：卡住必经之路、逼玩家绕路、或在贴身时完成拦截。

## 1. `strategy.js`：走迷宫策略

### 1.1 每 tick 的流程

```
读 observation
  ├─ 静态通道表 pass[x][y]（grid==0）
  ├─ 闸门：extra（进入代价）+1，closed（当前关闭的进不去）
  ├─ 机关：本 tick 激活的格
  ├─ 晶片、visited 集合
  ├─ 猎手位置表 hunterAt、猎手距离场 hd
  ├─ 风险场 risk（由 hd 推出）→ 权重 weight = 门代价 + 风险
  ├─ Dijkstra：costT[x] = x → 当前目标（钥匙 / 出口）的最小代价
  ├─ 若"下一步正好被猎手占据" → 再算一条封掉猎手格的距离场，看绕路是否便宜
  ├─ 决定要不要顺路捡晶片
  └─ 对 5 个候选动作（right/down/left/up/wait）线性打分，取最高分
```

### 1.2 目标选择

- 还没有钥匙 → 目标是 **钥匙**；已经有钥匙 → 目标是 **出口**。
- 目标格（钥匙格 / 出口格）在打分里加 `+1e6` 的巨大奖励：
  - 钥匙格必须踩（不踩就拿不到钥匙）；
  - 出口格必须踩（踩到即成功，此时掉血也已经不重要，见第 0 节第 1 条）。
  这条重奖励同时保证：即使猎手就站在钥匙/出口格上，玩家也会照踩不误，
  不会因为"怕掉血"而永远拿不到钥匙——那才是真正的死局。

### 1.3 三个距离场

| 场         | 含义                                | 算法                                              |
| ---------- | ----------------------------------- | ------------------------------------------------- |
| `costT[x]` | 从 x 走到当前目标的最小**加权**代价 | 二叉堆 Dijkstra（进入格子的代价 = 1 + weight[x]） |
| `hd[x]`    | 任意猎手到 x 的步数（0 = 同格）     | 多源 BFS                                          |
| `distP[x]` | 玩家到 x 的步数                     | BFS（只用来算"绕路捡晶片"划不划算）               |

`weight[x] = 闸门代价(0/1) + 风险代价`：

| 猎手距离 `hd[x]` | 风险代价              | 含义               |
| ---------------- | --------------------- | ------------------ |
| 0（同格）        | 12                    | 站上去基本必掉血   |
| 1                | 3；猎手这一拍要动时 6 | 贴身有被拦截的风险 |
| 2                | 1                     | 轻微               |
| ≥3               | 0                     | 无                 |

**为什么把风险折进代价场，而不是在打分时加惩罚？**
这是本策略最关键的一处取舍。早期版本用"候选格离猎手越近，扣分越多"的方式做躲避，
结果 runner 会出现**见猎手就逃**的行为：它被猎手一路赶进死角，最后死掉或超时。
把风险变成路径代价之后，"绕路"和"硬闯"变成了一次**全局比较**：
绕路 12 tick 以内划算（12 tick ≈ 36 分 < 1 点血的 167 分），超过就不绕。
于是"离猎手远"只在一个"确实值得"的范围内起作用，不会盖过"我要去出口"这件事本身。

**额外一条：猎手正好占住"下一步"时的绕路判定。**
如果按代价场算出来的下一步恰好是某个猎手所在的格子，策略会再算一条
"把所有猎手格临时封掉"的距离场：如果玩家绕过去只多花 ≤ `ALT_TOL(15)` tick，
就用这条绕路场当主代价场（等于把猎手格当成墙）；否则认为绕不掉，老老实实硬闯
（最多掉 1 血，掉 3 血才会死）。这条规则避免了"明知有猎手还一头撞上去"。

### 1.4 打分函数

统一把两种代价换算到同一个尺度上：

```
1 tick  ≈ TICK_COST = 3.0 分      （速度分：2000/maxTicks ≈ 2~6 分/tick）
1 点血 ≈ HP_COST  = 55 分         （生命分：500/3 ≈ 167 分/点）
```

单个候选动作 `c` 的分数（越大越好）：

```
score(c) = -3.0 * costUse[c]          // 路径代价（已含门与风险）
         + 8    (c 是晶片)            // 顺手就捡
         - 55   (c 是本 tick 激活的机关)  // 必掉 1 血
         - 12   (c 上有猎手)          // 同格硬冲突
         + 0.05 (c 没访问过)          // 探索分，几乎不影响主决策
         - 12 / -50 (这一步是"退回上一格")  // 反横跳惩罚
         - 60   (这一步是"回到两拍前的格子")  // 禁掉两格来回横跳
         - 30 / -6 / -1.5 (选 wait 且猎手在 1/2/3 格内)  // 别在猎手旁边发呆
         - 6*(stall-3) (选 wait 且原地已停滞超过 3 tick)
         + 1e6  (c 是目标格)
```

几个要点：

- **机关按"本 tick 是否激活"直接判死**：`-55` 远大于任何绕路收益，所以只要有别的走法，
  runner 绝不会主动踩激活的机关；实在只有这一条路，它会**等机关关闭再过**（等 1~4 tick，
  远便宜于掉 1 血）。机关在**下一拍**是否会激活也是可算的（`(tick+1+phase) % period < on`），
  所以"站在机关上等"的候选会被额外重罚。
- **"退回上一格"要罚**：早期版本没有这条，runner 会在猎手堵路时左右横跳（每拍 3 分的进展
  换来无限循环，最后超时）。第一次回头轻罚（-12），连续回头重罚（-50），逼它换一条路。
  仅仅罚"退回上一格"还拦不住 A→B→A→B 的两格循环，所以额外记一个"两拍前的位置"，
  回到它直接重罚（-60）。
- **停滞计数**：原地不动超过 3 tick 后，等待的惩罚随 tick 增长，防止"卡住等死"。
  闸门最多等 7 tick、机关最多等 5 tick，所以这个惩罚不会误伤正常的等待。

### 1.5 晶片策略

晶片分 1000 分（scout 8 片 → 125 分/片；expert 16 片 → 62 分/片），
1 tick 的速度代价只有 2~6 分，所以**顺路的晶片非常划算**。

规则：
1. 先算"绕路代价" `over = distP[coin] + costT[coin] - costT[player]`，
   `over ≤ COIN_TOLERANCE(12)` 才考虑；这个上限保证绕路花掉的时间（≈36 分）远小于晶片分。
2. 猎手在 5 格以内不去捡（`COIN_SAFE_DIST`）；已经在捡的中途猎手靠近到 3 格内就放弃。
3. 目标晶片写进 memory（`c` 字段），避免每 tick 在两个差不多近的晶片之间反复横跳。
4. 时间不够时（`maxTicks - tick` 减去到目标的代价 < 绕路预算）直接放弃捡晶片，保逃生。

### 1.6 状态记忆（memory）

`strategy.js` 返回的 memory 是一个小对象（几十字节，远小于 32768 字符上限）：

| 字段 | 含义                                      | 作用                       |
| ---- | ----------------------------------------- | -------------------------- |
| `c`  | 当前承诺去捡的晶片 `"x,y"`，没有则 `null` | 防止每 tick 换目标         |
| `d`  | 上一步的方向序号（-1 = 等待）             | 微小迟滞，避免闸门口来回抖 |
| `p`  | 上一个 tick 所在格 `"x,y"`                | 识别"回头"和"停滞"         |
| `q`  | 两个 tick 前所在格 `"x,y"`                | 识别 A→B→A 两格横跳        |
| `b`  | 连续回头次数                              | 反横跳惩罚的强度           |
| `st` | 连续未移动次数                            | 停滞惩罚的强度             |

**除 memory 外不保留任何状态**：没有随机数发生器，没有跨局缓存，
顶层变量在 `decide` 之外全部是纯函数用的常量表。同一局重放必然得到同样的轨迹。

### 1.7 复杂度

设 `N = width × height`（最大 35×25 = 875）：

- 每次 decide：1~3 次 Dijkstra（O(N log N)）+ 2~3 次 BFS（O(N)）+ 一次 O(N) 的候选打分。
- 实测单次 decide 的**算法部分**在毫秒量级（下面第 5 节有本地自测的量级参考），
  相对 200 ms 的上限有 100 倍以上余量；最坏情况也就再加一次 Dijkstra。
- 内存：几个长度 N 的 typed array（`Int32Array` / `Uint8Array`），约 875×4 B × 若干个，
  几十 KB 量级，可忽略。

## 2. `hunter.js`：追逐策略

### 2.1 为什么不能"追"

猎手 2~3 tick 才走一格，玩家每 tick 走一格。直线追、贪心追、路径追都只能跟在后面，
而玩家一旦领先，猎手永远追不上。所以猎手的目标不是"贴上玩家"，而是
**出现在玩家的前方，并让玩家为绕过它付出代价或掉血**。

### 2.2 玩家路线判定

猎手不知道玩家的意图，但知道玩家的**目标**（钥匙 / 出口都是公开的），
于是可以推断玩家的路线：

```
distP[x] = 玩家到 x 的步数
costT[x] = x 到目标（钥匙/出口）的步数
OPT      = distP[目标]
x 属于"玩家路线"  ⟺  distP[x] + costT[x] ≤ OPT + 3
```

也就是"存在一条经过 x 的、长度不超出最优解 3 步的路线"。这条带子里就是玩家大概率会走的格子。

### 2.3 站位价值

对每个追逐者单独算 `Hi[x]`（我到 x 的步数）。玩家到 x 需要 `distP[x]` tick，
我到 x 需要 `Hi[x] × hunterEvery` tick（我 2~3 tick 才走一格），
所以

```
余量 slack[x] = distP[x] - Hi[x] × hunterEvery
```

`slack ≥ 2` 才值得去（我得比玩家早到，而且要早得到能"站住"）。
在此基础上用 `val = 40·min(slack, 6·hunterEvery) - 8·costT[x] - 2·Hi[x]` 排序：
余量越大越好、越靠近目标越好、离我越近越好。

### 2.4 咽喉点评测（这一步让它比"傻追"强得多）

光是"堵在玩家路线上"还不够：玩家可以绕开，绕开就浪费 tick。
真正值钱的是**堵在绕不开的地方**。所以对排名前几的候选站位，
再算一次"把这个格子封死后，玩家要多绕多少步"：

```
detour[x] = dist(目标 → 玩家位置, 禁止经过 x) - dist(目标 → 玩家位置)
```

最终得分 `sc = detour × 6 + val`。也就是说：
**优先选那个"封住它能逼玩家绕最远"的点**，这才是真正的咽喉。

实现上：对每个候选点做一次"封格 BFS"，只对前 `TOP_CAND(6)` 个候选做（更靠后的候选
不会有更大 detour），并且按格子缓存结果，多个追逐者共享同一张表。

### 2.5 交战模式（贴身时）

当 `distP[我] ≤ ENGAGE_RANGE(3)` 时切换到交战：

1. **玩家被困住**：用 memory 记住玩家上一次轮询时的位置；两次轮询之间玩家没动，
   说明它被机关/闸门/猎手卡住了 → 我直接踩上它的格子，必中。
2. **拦截**：枚举玩家的合法邻格，挑一个"我一步能到、且玩家最可能走进去"的
   （用 `costT` 最小 = 最接近目标的邻格来近似玩家的下一步），我先一步占住那个格。
   玩家若走进来 → 同格 → 掉血。
3. **贴不上就压上**：`distP == 1` 时直接走进玩家的格子——
   玩家继续跑就是"擦肩换位"（不掉血），玩家停下就是同格（掉血），怎么都不亏。

### 2.6 多猎手分工

每个追逐者按顺序认领站位，被认领的格子不会再被后面的追逐者选（`claimed` 数组）。
于是 2~3 个猎手会自动散开去封不同的咽喉点，而不是挤在一起。

### 2.7 状态记忆（memory）

| 字段 | 含义                           | 作用                                  |
| ---- | ------------------------------ | ------------------------------------- |
| `p`  | 玩家上一次轮询时的位置 `"x,y"` | 判断玩家是否被困住                    |
| `s`  | 连续"玩家没动"的次数           | 同上（连续 2 轮没动基本可以确定卡死） |

猎手之间**不共享** memory，每个世界里的猎手各自持有自己的 memory
（协议规定玩家与追逐者、玩家世界之间都不共享变量）。

### 2.8 复杂度

每次 decide（每 `hunterEvery` 个 tick 一次）：

- 2 次 BFS（玩家距离场、目标距离场）+ 每猎手 1 次 BFS（我到各点的距离）+ 每个候选点 1 次"封格 BFS"，
  全部 O(N)；
- 站位候选排序 O(N log N)。

总代价 O(猎手数 × N log N)，同样在毫秒量级，远小于 200 ms 上限。

### 2.9 输出合法性

`actions` 里每个 `o.hunters` 中的 id **恰好出现一次**（遍历 `o.hunters` 构造），
不会多也不会少；action 只取 `'up'/'right'/'down'/'left'/'wait'` 五个字符串。
`memory` 是 `{p: string, s: number}`，可安全 JSON 序列化。

## 3. 设计取舍速查

| 取舍                       | 选择                                     | 理由                                                                              |
| -------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------- |
| 血 vs 时间                 | 血更贵（55 分/tick 单位 vs 167 分/点血） | 血分是实打实的 167 分/点，tick 只有 2~6 分；但绝不拿命换命（逃生 6000 分 > 一切） |
| 躲猎手 vs 硬闯             | 风险折进代价场，全局比较                 | 局部惩罚会让 runner 盲目逃窜、被赶进死角                                          |
| 绕路 vs 挨打               | 绕路 ≤ 12 tick 才绕                      | 12 tick ≈ 36 分 < 167 分/点血                                                     |
| 目标格上的猎手             | 无视，照踩                               | 成功先于伤害结算，躲它反而可能超时                                                |
| 换位（我进它格、它进我格） | 视为免费                                 | 协议明确豁免                                                                      |
| 站着不动                   | 重罚                                     | 猎手移动过来就同格                                                                |
| 回头                       | 重罚                                     | 否则会左右横跳到超时                                                              |
| 猎手贴脸猛追 vs 卡咽喉     | 卡咽喉                                   | 猎手只有玩家 1/3 速，追不上；但封住咽喉能逼玩家绕远路甚至撞上                     |
| 猎手站出口/钥匙上          | 禁止                                     | 目标格达成即结算，站那儿毫无收益                                                  |

## 4. 局限与已知弱点

**走迷宫策略**

1. **风险场是"当前快照"**：风险只按本 tick 的猎手位置算，猎手移动后风险场就变了。
   在猎手密集且移动频繁（expert：3 个猎手、每 2 tick 动一次）时，路径可能在两个方案间摇摆，
   表现为少量额外 tick。`b`（连续回头计数）能抑制一部分摇摆，但不能完全消除。
2. **代价场不含时间维**：机关/闸门的相位没有进入路径代价，只有"当前这一格能不能进"被考虑。
   因此 runner 是"走到机关前等它关"，而不是"提前规划好什么时候踩"，偶尔会多等 1~2 tick。
3. **晶片阈值是启发式**：`COIN_TOLERANCE = 12` 是按"晶片 ≈ 83~125 分 vs 1 tick ≈ 3.5 分"
   估的，偏保守。地图上晶片分布极端时（比如全挤在一个岔路口），这个阈值可能不划算。
4. **不建模"猎手的意图"**：runner 不知道猎手是要卡点还是要拦截，只能用距离场近似。
   面对"预测型"猎手（专门猜你下一格），runner 的规避是被动的。
5. **不做多步搜索**：只做 1 tick 的贪心 + 距离场，没有做"走 3 步看结果"的最短路搜索。
   在复杂迷宫里这会带来少量绕路。
6. **一旦被围死没有专门兜底**：如果猎手把玩家在一个小区域里封死，runner 只能硬闯掉血。

**追逐策略**

1. **咽喉点评测是近似的**：用"封住该格后距离场变长多少"来近似"这个点有多关键"，
   对多出口的复杂区域会有偏差；真正最优的封堵点需要割点分析，没有做。
2. **余量模型假设猎手匀速**：用 `Hi[x] × hunterEvery` 估算到达时间，
   忽略了闸门会让猎手额外等待。
3. **玩家路线是静态推断**：只按"到钥匙/出口的最短路"推断，
   玩家如果为了捡晶片临时改道（尤其是我们的 runner 就会），
   猎手的封堵点可能对不上；这时靠交战模式兜底。
4. **站位是"我先到"的最优解，不是全局最优博弈**：多个猎手之间是贪心认领，
   不是联合优化，可能出现两个猎手封了等价价值的点。
5. **没有利用"猎手不受机关伤害"这一优势**：理论上猎手可以站在机关格上堵路
   （玩家不敢踩），本策略没有专门偏好机关格作为站位。

## 5. 本地自测说明（**非官方环境**）

为了验证两份脚本不会抛异常、不会输出非法动作、并且能跑出合理结果，
我在交付目录之外写了一个**自用的**测试脚本（开发期临时脚本，不在本次交付物内），
它包含：

- 一个自写的迷宫生成器（DFS 挖通道 + 随机开环 + 随机放钥匙/出口/晶片/机关/闸门/猎手），
  **与官方生成器无关**，因此地图难度分布和官方不一样；
- 一个按协议文字实现的结算模拟器（玩家先动 → 成功判定 → 猎手移动 → 伤害判定 → 推进 tick），
  并校验 hunter 返回的 id 集合与 `o.hunters` 完全一致。

在 30 个种子 × 3 个难度上的**本地**结果（每档 30 局，同一 seed 列表）：

| 难度     | 对本仓库 `hunter.js`                                         | 对"直线追玩家"参考猎手                      |
| -------- | ------------------------------------------------------------ | ------------------------------------------- |
| scout    | 成功率 100%，平均结束 tick 84，平均血量 2.7，平均晶片 4.7/8  | 成功率 100%，tick 84，血量 2.5，晶片 4.7/8  |
| standard | 成功率 90%，平均结束 tick 122，平均血量 2.0，平均晶片 4.9/12 | 成功率 97%，tick 123，血量 2.0，晶片 4.9/12 |
| expert   | 成功率 83%，平均结束 tick 144，平均血量 1.6，平均晶片 5.4/16 | 成功率 87%，tick 150，血量 1.7，晶片 6.2/16 |

同一批地图上把 `hunter.js` 换成"只会直线追玩家"的参考实现，runner 的得分普遍更高
（standard 8213 → 7717，expert 7426 → 7106），完成 tick 也更短，
说明卡咽喉点的策略确实比硬追更有效。

单次 `decide` 的算法耗时：`strategy.js` 约 1~2 ms、`hunter.js` 约 1~7 ms（Node + vm 环境，
含 JSON 解析开销，比浏览器慢），相对 200 ms 上限余量很大。
文件体积：`strategy.js` 约 12.7 KB、`hunter.js` 约 9.1 KB，均远小于 100 KB。

**这些数字只能说明"脚本行为合理、能跑通、能复现"，不代表官方环境下的成绩**：
地图生成器、猎手抽签、对手水平、官方结算实现都可能不同。
上面正文里没有引用任何未经验证的"实测最优"结论。
