# 将军棋策略：梯度洪流（Gradient Tide）

`strategy.js` 是一个纯同步、无依赖、完全确定性的将军棋（junqi-2）策略。  
顶层只导出一个入口 `function decide(observation)`，不使用 `import` / `export` /  
第三方库 / 动态模块 / `importScripts` / 额外 Worker，也不触碰 `Date`、  
`performance`、`Math.random`、`crypto` 等任何非确定性输入。

核心思想一句话：**把"下一步该往哪儿打"变成一个距离场问题——每个 tick 重算一次  
"价值距离场"，然后在 4 条移动的预算内，贪心捡最赚的格子吃。**

---

## 1. 总体架构

每个 tick 的决策分七步，全部同步完成：

| 步骤 | 内容                                       | 开销         |
| -- | ---------------------------------------- | ---------- |
| 1  | 合并地形记忆（memory → Int8Array，再叠加本 tick 新情报） | O(N)       |
| 2  | 快照当前可见的 `owner` / `army` 到 TypedArray    | O(N)       |
| 3  | 维护敌方将军记忆表（新增 / 刷新 / 清除已死亡）               | O(N)       |
| 4  | 多源 Dijkstra 建立"价值距离场"                    | O(N log N) |
| 5  | 将军周边威胁评估，决定是否进入防守模式                      | O(R²)      |
| 6  | 在 4 条移动预算内贪心选招，本地模拟结算                    | O(N)       |
| 7  | 输出 `{moves, memory}`                     | O(N)       |

其中 N = 宽 × 高，最大为 168 × 164 = 27552（16 人辽阔场地）。

---

## 2. 状态记忆设计

协议规定 `owner` / `army` 只在当前可见时给出，视野外一律未知；而 `terrain`  
一旦侦察过就保持已知。策略据此把 memory 压缩成两样东西：

### 2.1 地形图 `memory.t`

一个长度恰为 N 的字符串，每格一个字符，取值 `-1..3` 分别编码为 `'0'..'4'`  
（即 `charCode - 49`）。每 tick 用新观察覆盖已知格，**旧情报永不丢失**——  
即使一块领地被敌人夺走，我们依然记得那里是城市还是山地。

选字符串而不是数组，是为了压在 32768 字符的序列化预算内：最大地图  
168 × 164 = 27552 字符，加上将军表，实测序列化后约 27.6 KB，留有裕量。

### 2.2 敌方将军表 `memory.g`

形如 `[[playerId, x, y, lastSeenTick], ...]`。维护规则：

- **新增/刷新**：本 tick 观察到某格 `terrain === 3` 且归属不是自己/队友时，  
  记录或更新其位置与发现 tick；
- **清除**：`players[id].alive === false`（已出局），或该格地形已被观察为  
  非 3（将军被攻陷后变成城市），或该格当前归属已是自己/队友。

### 2.3 为什么不记更多

`owner`/`army` 的视野外值是"未知"，存下来只会误导。而**己方格子必然全部可见**  
（视野定义就是"所有己方格子的 8 邻域并集"），这条性质带来一个关键推论，  
见下一节。

---

## 3. 迷雾的信息学利用

**关键观察：任何与我方格子四邻接的格子，一定落在某个己方格的 8 邻域内，因此  
一定当前可见。**

这意味着：

- 每一次移动的**目标格的 terrain / owner / army 全部已知**，不存在"蒙眼赌兵"；
- 我们能看到的敌军就是贴脸的敌军；敌军的纵深部署永远不可见，因此策略不试图  
  预测远方敌情，只对"接壤格"做决策；
- 迷雾的实际影响只剩下三处，并已分别处理：
  1. **敌方将军位置**——靠 `memory.g` 长期记忆，作为远程进攻目标；
  2. \** Dijkstra 的中继穿越\*\*——未侦察格穿越代价设为 3（高于己方 1、中立 2），  
     让军队优先走已知安全的路线；
  3. **敌方兵力总量**——`players[].army` 是全员公开的，用来判断强势/弱势，  
     切换进攻姿态。

换句话说：本策略把"探图"完全交给扩张本身——每吃掉一块新地，迷雾就自动后退一格。

---

## 4. 价值距离场（每 tick 的核心计算)

### 4.1 目标与权重

Dijkstra 是多源的，源点分两类：

- **接壤可争夺格**：与我方领土四邻接、且非己方/队友的格子。初始距离：
  - 城市 `2`：权重 0（最想打）；
  - 中立空地：权重 2；
  - 敌方领土：权重 `enemyGoalW`。
- **记忆中的敌方将军**：初始距离 0（最高优先级，压过一切）。

`enemyGoalW` 是姿态参数：当我方总军力 > 2.2 × 敌方总和 + 20、或我方领土 >  
1.6 × 敌方总和 + 10 时取 2（主动进攻），否则取 4（优先扩张、少啃硬骨头）。

### 4.2 边代价

Dijkstra 松弛时，进入不同区域的格子代价不同：

| 进入的格子   | 代价 | 理由               |
| ------- | -- | ---------------- |
| 己方/队友后方 | 1  | 畅通，鼓励军队在后方快速机动   |
| 中立      | 2  | 正常扩张             |
| 未侦察（迷雾） | 3  | 可通行但不诱人，避免军队扎进未知 |
| 敌方占领    | 5  | 尽量绕开强敌区域，减少无谓消耗  |

于是 `dist[i]` 的语义是：**从格子 i 出发，到达"最近的一个高价值目标"的总代价**。  
比较对象不是单纯的步数，而是"步数 + 穿过的风险"。

### 4.3 实现

二叉堆用数值编码 `dist * N + idx` 压成单个 number 入堆（最大  
约 1.4×10⁵ × 27552 ≈ 3.8×10⁹，远小于 2⁵³，安全），堆操作手写，无依赖。

## 5. 移动选择（4 条预算内的贪心)

对每个候选移动，依次检查：

1. **出发格**：是己方/队友、军队 ≥ 2、本 tick 未被用过、距离场可达；  
   将军格额外要求军队 ≥ 3（早期将军只有 1~2 军时不动作）；
2. **目标格**：地形可通行、非己方/队友、且 `dist[目标] < dist[出发]`  
   ——即**严格沿梯度指向高价值目标**，防止军队在原地打转或倒吸；
3. **吃得下**：设守军为 `d`，半出兵 `k = floor(n/2)`，全压 `k = n-1`：
   - `k_half > d`：用半出兵（`half: true`），优先保留一半守家；
   - 否则 `k_full > d`：仅在**收益足够**时全压——目标是将军、是城市、  
     或（敌方领土且 `k_full - d >= 3`）；否则跳过，让兵力继续攒；
   - 两者都吃不下：跳过，**绝不做无谓送兵**。

打分（越高越优先，同分按格子索引确定，保证可复现）：

```
score = 目标价值 + 0.5 × min(出发兵力, 80) - (全压 ? 40 : 0) - 聚集惩罚
目标价值：敌方将军 1000 ／ 城市 300 ／ 敌方领土 120 ／ 中立空地 60
聚集惩罚：出发格与本 tick 已选出发格切比雪夫距离 ≤ 3 时 -30
```

每选中一条就做一次**本地模拟结算**（`出发格 -= k`、目标格归属改为自己、  
`目标格 = k - d`），并把出发格与落点都标记为已用。本地模拟让后续选择看到  
本条指令的结果，避免两条指令互相拆台；落点标记则防止同一股兵力在一 tick 内  
被反复拆分转移。

### 5.1 为什么要"聚集惩罚"

4 条移动如果不加约束，会永远集中在全图兵力最雄厚的同一个角落（因为打分里  
有 `0.5 × min(n, 80)`）。聚集惩罚迫使移动在空间上铺开，让整条边疆同时推进，  
而不是把一个点堆成孤峰。

## 6. 防守模式

每 tick 检查将军周围切比雪夫距离 4 的方框：

- `threatArmy` = 框内可见敌军兵力之和；
- `myNear` = 框内我军兵力之和 + 将军格兵力。

若 `threatArmy > myNear × 1.5 + 2`，判定为"被压"，进入防守模式：

- 将军格**不出兵**（保命优先，将军死了直接出局）；
- 只允许"目标在将军附近 4 格内且为敌方"的反击移动；
- 不再向中立地扩张，全军收拢应对贴脸威胁。

这是一把双刃剑（见"局限"），但将军被偷的损失远大于几块地，故阈值偏保守。

---

## 7. 组队与中立

- 通过 `players[].team` 建立 `teamOf` 表，队友格子一律视为己方：不攻击、  
  可被 Dijkstra 当作廉价后方通行；
- 自由混战下 `team === id`，逻辑自动退化为"只认自己"；
- 中立城市只是高驻军（40~50）普通格子，没有特殊规则分支——它天然会被  
  "城市权重 0 + 吃得下才打"的逻辑处理：边疆兵力会在城边自然堆积，直到  
  `k > 守军` 的那一 tick 被吃掉。

---

## 8. 复杂度

- **时间**：主体是一次 Dijkstra，`O(N log N)`；其余为若干 `O(N)` 扫描。  
  最大地图 N = 27552，本地实测平均每次 `decide` 约 **5~7 ms**  
  （Node 22，普通桌面 CPU），相对 200 ms 预算有约 30 倍裕量，  
  初始化 1500 ms 预算几乎用不到（代码无预热需求）。
- **空间**：若干长度为 N 的 TypedArray（`Int8Array` / `Int32Array`），  
  约数百 KB；memory 序列化后最大约 27.6 KB < 32768。
- **通信**：无异步、无消息传递、无定时器，`decide` 同步返回。

---

## 9. 可复现性

- 无任何随机源；所有随机需求（例如没有）都不存在；
- 全部遍历按固定顺序（格子索引升序、方向 `up/right/down/left`）；
- 平局用严格大于 `>` 打破，先到者（索引小者）恒胜；
- 同一 observation 序列必然产生同一输出序列，与播放速度、真实时间无关。

---

## 10. 局限（如实说明）

1. **单 tick 贪心，没有搜索**。不做任何多步推演（不模拟未来 tick、  
   不做 minimax / MCTS），因此看不到"这看着赚、下一步被反吃"的陷阱。
2. **不建模对手**。不记敌方兵力历史、不识别对手风格、不预测其意图；  
   防守模式只看当前贴脸的兵力对比。
3. **没有显式的增援调度**。后方的大 stack 只会沿距离场自然流向边疆，  
   不会主动向某个攻坚目标集中；打 40~50 驻军的城市靠的是边疆自然堆积，  
   效率不高。
4. **没有队伍协同**。队友只是"不攻击 + 可通行"，不会配合夹击、  
   不会让地、不会共享将军位置。
5. **扩张速度约为一圈/tick**。距离场的梯度特性决定了同一条边疆每 tick  
   大约推进一格（4 条移动分摊在整条边疆上），早期抢地可能偏慢。
6. **防守模式可能被多线牵扯**。阈值触发后会全面停止扩张，若敌方只是佯动，  
   会白送发展时间。
7. **对"断点"不敏感**。被敌人切断的飞地不会被识别为孤军，仍按普通边疆处理。

## 11. 主要设计取舍

| 抉择                 | 选择           | 理由                                  |
| ------------------ | ------------ | ----------------------------------- |
| Dijkstra vs 普通 BFS | Dijkstra     | 需要"穿越敌占区更贵"的软惩罚，BFS 无法表达            |
| 目标权重：城市 > 敌将？      | 敌将权重 0，城市也 0 | 城市在"接壤格"里权重 0 已经最高；敌将额外作为远程源点，二者不冲突 |
| 半出兵 vs 全压          | 默认半出兵        | 保留一半守家；全压只在"确定吃下且收益足够"时使用           |
| 吃不下时               | 跳过，攒兵        | 宁可不推进，也不送兵（送掉的兵还会变成对方的兵力）           |
| memory 只存地形 + 敌将   | 是            | 序列化预算 32768 字符，全图地形字符串已占满大半         |
| 是否做内部增援            | 不做           | 实现复杂度高、收益不确定；距离场已提供部分"自动集结"效果       |
| 防守阈值               | 保守（1.5×）     | 将军被偷直接出局，代价不对称                      |

## 12. 本地验证情况（如实声明）

开发过程中自建了一个**遵循本协议规则的最小仿真器**（移动按  
`(tick + i) mod N` 轮转结算、生产公式 `g = 1 + floor(tick/200)`、  
迷雾视野为己方格 8 邻域并集、击杀将军后领土转让与地形变城市均已实现），  
并用它做了以下检查：

- 5 局完整对局（2/4/8/16 人，覆盖紧凑 13×11、标准 24×22、辽阔 40×36  
  与 168×164 四种尺寸）：**0 次异常、0 次非法输出、0 次 memory 超限**；
- 2 局自对弈（4 人、6 人）：无异常、无早退，对局正常打到 maxTicks；
- 9 个边界用例：tick 0 无兵可动、memory 回灌、玩家已死亡、  
  被山完全围死、将军被贴脸（不出兵）、能击杀将军时必出击、  
  兵力不足半出兵时自动全压、确定性（同输入同输出）、最大地图 memory 体积；
- 性能：最大地图平均每次 `decide` 约 5~7 ms。

**必须说明**：本地仿真器不是官方环境，对手机器人是协议示例里给出的  
"每 tick 打一条移动"的简易 bot，因此以上数字**只能证明代码的正确性、  
稳定性与性能余量，不能推断真实对战排名**。文中所有关于战斗力的描述均为  
算法设计层面的预期，不构成实测结论。
