# 将军棋策略说明（协议 junqi-2）

本文件对应 `strategy.js`。策略是一个**纯函数式的确定性贪心 + 局部模拟器**：每 tick 读入 `observation`，
在本地棋盘副本上枚举"我方每一格 → 四个方向"的所有合法动作并打分，挑出分数最高的至多 4 条指令依次下发。

文件里没有任何 `import` / `export` / 第三方依赖，不访问网络、DOM、存储，也不使用 `Date`、`Math.random`、
`crypto` 等非确定性输入；同一份 observation 必然得到同一份输出，因此满足"可复现"的要求。

---

## 1. 总体结构

一次 `decide(o)` 调用分六步：

| 步骤 | 做什么 | 关键产出 |
| --- | --- | --- |
| ① 读盘 | 把 `terrain/owner/army` 三个二维数组摊平成 `Int8Array/Int16Array/Int32Array` | 扁平棋盘 |
| ② 更新记忆 | 把"看得见的将军格/城市格/敌方占格"写进 `memory` | 跨 tick 的长期信息 |
| ③ 态势评估 | 己方统计、敌方将军列表、两次 BFS 距离场、家门威胁扫描 | `distMe` / `distTarget` / `distDef` |
| ④ 选焦点 | 在"敌将 / 中立城 / 猎杀目标"之间选一个推进焦点 | `focusIdx` |
| ⑤ 生成候选 | 枚举每个己方格 × 4 方向，过滤非法后打分 | 候选表（TypedArray） |
| ⑥ 模拟执行 | 选最高分动作 → 在本地棋盘上结算 → 局部刷新派生量 → 再选下一个，最多 4 条 | `moves` |

第 ⑥ 步是这套策略的骨架：因为协议规定"同一 tick 内前一指令的结果对后续指令可见"，
所以策略用**同一份本地模拟棋盘**逐条结算，从而支持"甲→乙→丙"的同 tick 连续冲锋：
打掉边界守军后，残兵自动出现在新格上，下一条指令可以立刻从新格继续打。

## 2. 战术思路

### 2.1 扩张：薄铺快扩，把每一分兵力都变成地产

在 `junqi-2` 的结算规则下，**普通土地每 25 tick 产 1 兵**（产出 `g = 1 + floor(tick/200)`），
所以"多占一格"等于"长期多产兵"。因此策略在扩张期的核心诉求是**尽快把中立空地和未知地形变成自己的格子**：

- 进入中立空地（`owner = -1`）：基础分 250，外加"邻接未知地形" +60、"邻接敌方" +70；
- 进入未侦察地形（`owner = -2, terrain = -1`）：基础分 250 + 45 ×（其 8 邻域内未知格数量），
  也就是**优先去开"未知的未知"**，一次侦察换回更多视野；
- 扩张移动用 `half: true`（送出一半），源格因此总是留有驻军，不会被一次偷袭清空。

> 设计取舍：早期版本给每个格子设了"留兵底线"（源格至少留 2 兵、新格至少 2 兵），
> 出发点是避免满地图都是 1 兵小碎块导致打不出拳。本地模拟器的对照实验否掉了这个想法：
> 留兵底线把扩张速度压慢了一个数量级（平均分从约 5600 掉到约 1100），
> 因为"薄铺"带来的地产增量远比"每格多留一个兵"值钱。最终只保留了对**己方将军/城市**的最低卫戍。

### 2.2 打城：城池是全局最重要的经济资产

按协议的经济模型，一座城每 tick 产 `g` 兵，而 `g` 会随时间从 1 涨到 6。
在 1200 tick 的标准局里，**一座城累计能产出与将军同量级的兵力**，而它的驻军只有 40~50 且不再增长。
也就是说：吃掉一座中立城的投入是一次性的 40~50 兵，回报却是几千兵。

所以策略：

- 扫视全图地形（地形是**永久记忆**的），找出所有还没被占用的中立城市；
- 用 BFS 距离场挑出**离自己最近的那座**，把它设为"焦点"，全队往那儿推；
- 邻接中立城且兵力足够时，攻击分给到 1300（仅次于斩敌将），确保"有城必打"；
- 只有在"打完之后全队总兵力还剩不下 10 兵"时才放弃，避免把家底打光。

### 2.3 搜将军与斩将

- 敌将的格子是地形 `3`，而**地形一旦侦察过就永久保留**，所以只要见过一次就再也忘不掉；
  策略把 `(格子 → 归属玩家, 驻军, 观测 tick)` 存进 `memory`，即使后来那格视野外（`owner = -2`）也能复原。
- 击杀敌方将军有 3 重收益：击杀分（`1500 × 击杀数 / 敌方人数`）、对方全部领土归我（兵力减半）、
  以及直接终结一个对手。所以对敌将格的攻击分高达 6000，全局最高。
- **猎杀模式**：在还没摸到敌将、附近又没有城可打时，策略用"见过的敌方占格集合的质心"
  推测敌方首都的大致方位（敌方的领土是围绕他们将军长出来的，质心是个粗略但有效的估计），
  朝那个方向推进。推进过程中会不断揭开敌方纵深的地形，一旦进入将军 1 格范围，
  地形 `3` 立刻被记住，焦点就切换成真正的敌将并转为精确打击。
  猎杀模式把本地模拟器里的平均击杀数从 0.13 提到 1.13。

### 2.4 进攻与防守的取舍

**进攻优先。** 敌方格的基础攻击分是 `500 - 0.9 × 守军`，且分阶段放大（早期 ×1.0、中期 ×1.2、后期 ×1.5），
远高于扩张的 250；只有当 `发送兵力 ≤ 守军`（打不过）时才放弃该方向——所以策略**从不主动送人头**，
每次进攻都要求严格大于守军。

在此之上有两档"抢分"加成：

- 目标格与我方将军/城市相邻（`prio`）：加到 `2000 - 守军`，用于打掉贴脸的敌人；
- 目标格与敌方将军相邻：加到 `900 - 守军`，为下一刀斩将铺路。

**防守是有条件的。** 策略先扫描"己方将军周围 3 格内的敌军规模"，
只有当**敌军堆得比我家将军自己的卫戍还厚**（`threat > 将军驻军`）时才判定为真危险，
这时才：① 抬高将军/城市的最低卫戍；② 给出"往将军方向靠拢"的额外加分，把兵拉回来。
在模拟器上，无条件回防会让平均分从约 5600 掉到约 1600（过度回防等于放弃进攻节奏）；
改成"精准回防"之后两项指标同时变好（对基线 5833 分 / 自对自 3098 分，存活率 7/10）。

### 2.5 迷雾信息的利用

- **地形是免费的永久记忆**：`terrain` 数组本身就是引擎维护的已侦察地形，策略直接拿来用，
  所以"敌将在哪座山后面"这类信息是免费的。
- **归属与驻军才是真正需要记忆的**：`owner`/`army` 只在当前视野内给出，视野外是 `-2`/`-1`。
  策略把三类信息写进 `memory`：
  - `genInfo`：见过的敌方将军格（归属玩家、驻军、观测 tick）；
  - `cityInfo`：见过的城市格（归属、驻军、观测 tick），用来在视野外估算驻军；
  - `enemySeen`：见过的敌方占格（最多 300 条，最新的优先），用于猎杀模式的质心估计。
- **驻军推算**：视野外的将军/城市，用"上次观测的驻军 + `g × 流逝 tick`"估算生产增量
  （只有将军和城市产兵，中立城市驻军恒定）。
- 视野内的守军永远是精确值：只要一个格子与我方格子 4 向相邻，它必然在 8 邻域视野内，
  所以"打邻居"时守军一定看得见——策略据此把"看不见的敌人"一律视为不可主动进攻对象。

## 3. 状态记忆（`memory`）

`memory` 是任意 JSON 值，策略实际使用一个对象：

```jsonc
{
  "genInfo":  { "<格子下标>": { "id": 玩家id, "a": 驻军, "t": tick } },  // 见过的敌将
  "cityInfo": { "<格子下标>": { "id": 玩家id, "a": 驻军, "t": tick } },  // 见过的城市
  "enemySeen": { "<格子下标>": { "t": tick } },                         // 见过的敌方占格（猎杀用）
  "assault":  { "idx": 目标格下标, "until": tick }                       // 进攻承诺
}
```

- 全部是普通对象/数字，**可 JSON 序列化、无循环引用、无 BigInt、全部有限**；
- `genInfo`/`cityInfo` 各上限 400 条、`enemySeen` 上限 300 条，超出时按观测时间淘汰最旧的，
  因此 `memory` 体积有上界（实测序列化后远小于 32768 字符限制）；
- `assault` 是"进攻承诺"：一旦锁定某个敌将，就持续追着它打（除非出现明显更近的新目标），
  避免在多个目标之间反复横跳、每 tick 都在原地换目标。

## 4. 复杂度与性能

记 `N = width × height`，`C` 为己方格子数（`C ≤ N`），`E` 为候选动作数（`E ≤ 4C`）。

| 环节 | 复杂度 | 说明 |
| --- | --- | --- |
| 读盘 + 记忆更新 | `O(N)` | 三次数组摊平 + 一次扫描 |
| 敌我判定 / 己方统计 / 邻域统计 | `O(N)` | 每格固定 8 邻域 |
| BFS 距离场 | `O(N)` | 每 tick 2~3 次（我方→全图、焦点→全图、可选的家门→全图） |
| 候选生成 | `O(C)` | 每格 4 个方向，各 O(1) 打分 |
| 逐条模拟执行 | `O(4 × E)` | 每条指令后只刷新受影响格子的派生量与分数，扫描整张候选表 |
| 整体 | `O(N)` 每 tick | 内存 `O(N)` |

工程上做了三件与"每次调用只有 200ms"直接相关的事：

1. **工作区复用**：棋盘数组、派生量数组、候选表都按地图尺寸缓存复用，避免每 tick 产生几 MB 临时对象引发 GC 抖动；
2. **增量刷新**：一条指令执行后只重算"起点/终点 3×3 邻域"内受影响的候选分数，而不是全量重算；
3. **热路径无全局查找**：全部实现包在 IIFE 里，地形常量取为函数内局部量，
   方向表、棋盘数组都用局部变量持有——这一点在实测中影响巨大（同一份代码在
   `eval` 环境下因为脚本级变量走动态查找，单次 decide 慢了 20 倍）。

## 5. 局限与已知弱点

1. **多人局偏弱**。在本地模拟器上，4 人局对基线脚本平均约 5800 分、2 人局约 8700 分，
   但 8 人 / 16 人局只有约 900 分，而基线脚本在同样局面约 1500 分。
   原因判断：地图大、玩家多时"集中兵力推向一个焦点"的收益被摊薄，
   而基线那种"见敌就打"的散兵式进攻在抢地产/抢产能上更高效。
   多玩家局我方的改进方向是：把焦点从"单点"改成"按收益排序的多个目标"，或降低集结强度。
2. **视野外守军是估算值**。中立城市驻军恒定，所以估算准确；但敌方将军/城市在视野外的驻军
   是"上次观测 + 产出推算"，如果对方在中途把兵调走，估算会偏高，导致我们错过一个本可以打掉的窗口。
3. **不会算"差一步就能斩将"的最优路径**。当前是"朝焦点直线推进"的贪心，
   没有做全局搜索（最小代价破防路径、最优集兵点），在敌方防线很厚时可能反复撞同一堵墙。
4. **不处理队友协作**。组队在规则上只是"同队可互相增援"，策略对队友格子的处理等同于己方格子，
   没有做分工（谁是主攻、谁负责挡刀）。
5. **对"极规整"的对手缺少反制**。策略没有专门识别"龟缩型/满城型"对手，
   遇到对方全城防守时，可能把兵耗在打城上而不是绕后找将军。
6. **本地模拟器 ≠ 官方环境**。本文所有数字都来自我自己写的简化模拟器
   （见 `sim.js`，它按协议的结算顺序实现了视野迷雾、战斗、将军被攻陷、生产与胜负判定），
   **不是官方评测环境实测**。模拟器的地图生成、对手脚本、结算细节都可能与真实环境有出入，
   数字只能用于横向比较不同版本，不能当作真实胜率。

## 6. 调参与验证方式

- `strategy.js` 里所有关键权重都是"魔法数字"，集中放在各评分函数中，便于调整；
- 本地对照实验（同一批随机种子、同一批对手、只改一个参数）覆盖了：
  留兵底线开关、进攻基础分与阶段系数、扩张分、抢城分与门槛、猎杀开关与集结权重、
  回防开关、扩张派兵上限等；
- 结论是本文件第 2 节写的那套配置（薄铺扩张 + 进攻优先 + 有条件回防 + 城/将焦点）
  在本地模拟器上综合最好。
