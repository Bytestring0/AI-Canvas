# 将军棋策略说明（junqi-2）

本文说明 `strategy.js` 的算法结构、状态记忆、复杂度、已知局限与设计取舍。  
文末"本地验证"一节会明确区分**我实际跑过的自建模拟**与**官方引擎结果**——后者我没有，也不会编。

## 0. 交付物

| 文件          | 内容                                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `strategy.js` | 单文件策略，顶层仅定义 `decide(observation)` 与若干常量/内部函数。无 `import`/`export`、无第三方包、无网络、无 DOM、无 `Date`/`Math.random`。 |

## 1. 从规则里挖出的四个关键事实

整套策略建立在这四条观察上，它们决定了算法能有多简单。

### 1.1 所有"可攻击格"必然可见 —— 战斗判定不需要任何估算

> 视野 = 所有己方格子的 8 邻域并集。

一个格子只要能被我方某一格**正交**走到，它就在那一格的 8 邻域里，因此必然处于可见状态，`owner` 与 `army` 都是精确值。

这条推论的价值极大：**每一次进攻的胜负是确定可知的**，不需要像常规战争游戏那样对迷雾里的守军做概率估计。于是"打不赢就不打"可以做成硬约束——`k ≤ 守军` 的移动直接不生成，策略永远不会白送军队。

（代码里仍保留 `if (ot === -2) continue;` 的防御性判断，防止实现细节与预期不符。）

### 1.2 `terrain` 由服务器永久保存 —— 不需要自己存地图

> `terrain` 一旦侦察过就保持已知。

所以策略**完全不存地图**。山地、城市、将军位置全部现读现用。这让记忆体小到几乎可以忽略，也消除了"本地地图与服务器不同步"这类 bug 的来源。

### 1.3 `half` 与全量移动是两种完全不同的运兵方式

| 方式                 | 移动量       | 出发格剩余  | 连续使用 4 次的衰减      |
| -------------------- | ------------ | ----------- | ------------------------ |
| `half: true`（默认） | `floor(n/2)` | `ceil(n/2)` | 每步**减半**（几何衰减） |
| `half: false`        | `n - 1`      | `1`         | 每步只损失 **1**         |

这直接决定了两种用法：

- **长距离投送 / 突击**必须用 `half: false`。一支 200 军的部队走 4 格还剩 196，用 `half` 就只剩 12。
- **就地扩张 / 需要留纵深**用 `half: true`。出发格保留一半，被反打时不至于一触即溃。

策略据此做了一个二选一（见 §3.3）：**朝目标推进的步子用全量，其余用半量；从自家将军出发永远用半量。**

### 1.4 产能结构与计分权重决定了"土地优先"

产量 `g = 1 + floor(tick / 200)`，将军与己方城市每 tick `+g`，普通土地每 25 tick `+g`。

在 1200 tick 的对局里，中期之后 `g` 已经到 4~6，此时几百格土地的产量（每 25 tick 一次，平均每 tick `land × g / 25`）会远超将军和城市的固定产出。而计分里：

- 领土 2000 分 = `己方土地 / 全体玩家土地`
- 军力 2000 分 = `己方军队 / 全体军队`

两者合计与"获胜"的 4000 分等值，而且**土地本身就是军力的上游**。所以策略的总基调是：**以最快速度把地占满，用土地换产能，用产能换军力，军力只在能净赚的时候才花出去。**

顺带一个推论：抢**敌方**土地比抢中立土地更划算——中立地让分子 +1、分母也 +1；敌方地让分子 +1、分母不变。代码里对应 `+70` 与 `+40` 的差异。

## 2. 每个 tick 的处理流水线

```
decide(o)          —— 只做 try/catch 兜底，异常时返回 {moves: [], memory: null}
 └─ decideInner(o)
     ├─ 0. 取出/修复 memory
     ├─ 1. 建玩家表（team / alive）
     ├─ 2. 把 terrain / owner / army 展平成 Int8Array / Int16Array / Int32Array
     ├─ 3. 维护敌方将军记忆（见 §5）
     ├─ 4. BFS(dMe)      —— 从自家将军出发的距离场
     ├─ 5. 威胁评估      —— 6 步内敌军"抵达时剩余兵力"的最大值
     ├─ 6. 目标选择      —— 守家 / 斩首 / 打城 / 纯扩张
     ├─ 7. BFS(dGoal)    —— 从目标出发的距离场（目标就是自家将军时直接复用 dMe）
     └─ 8. 贪心挑 4 步 + 影子结算（见 §3）
```

### 2.1 为什么用 BFS 而不是曼哈顿距离

地图有山地，且未知地形按"可通行"乐观处理。用 4 邻接 BFS 得到的距离场能自然绕开已知山地；同时它给出一个"梯度"，相邻格子的距离差通常为 1，可以直接当作"往哪个方向走更靠近目标"的判据。

未知地形（`terrain === -1`）当作可通行，是因为规则保证"全部可通行格子互相连通"，且山地只占少数。乐观处理会在极少数情况下高估某条路径的可达性，但不会产生非法指令——真正能不能走由第 7 步的邻接检查兜底。

### 2.2 威胁模型

对每个可见敌军格 `i`：兵力 `a`、到自家将军的 BFS 距离 `d`，则它抵达将军时大约剩 `a - d`（全量移动每步掉 1）。取 6 步内 `a - d` 的最大值记为 `threatNear`。

当 `threatNear > 将军驻军` 时，判定为**守家模式**，目标切换成自家将军，全军回防。

### 2.3 目标选择优先级

```
1) threatNear > 将军驻军            → 守家（目标 = 自家将军）
2) 已知敌方将军，且不比最近城市远太多 → 斩首
3) 已知城市                         → 打城
4) 其余                             → 纯扩张（无目标）
```

"远太多"的判据是 `dMe(敌将) <= dMe(城) + 6`。将军只被目击过才会进入候选，位置永久记在 `memory` 里（见 §5）。

## 3. 打分函数

每一轮（共 4 轮）遍历所有"己方、军队 ≥ 2、本 tick 还没出发过"的格子，对 4 个方向各算一个分，取全局最高分执行；执行后**在影子状态上结算**，再进入下一轮。

### 3.1 进攻（目标是敌方或中立格）

| 项                  | 取值                                                    | 意图                                         |
| ------------------- | ------------------------------------------------------- | -------------------------------------------- |
| 基础占领分          | `+100`                                                  | 只要能赢，占领本身就值得做                   |
| 目标靠近            | `+(dGoF - dGoT) × goalW`，`goalW = max(0, 48 - 4·dGoF)` | 在目标附近形成矛头；离目标 12 格以外权重归零 |
| 向外扩张            | `+(dMeT - dMeF) × 30`                                   | **始终存在**，保证任何方向都在长             |
| 城市                | `+900`                                                  |                                              |
| 敌方将军            | `+60000`                                                | 斩首收益压倒一切                             |
| 敌方土地 / 中立土地 | `+70` / `+40`                                           | 见 §1.4                                      |
| 兵力偏好            | `+min(n, 50) × 0.8`                                     | 优先动用大股部队，减少"细碎调兵"             |
| 过度投入惩罚        | `-(k - need) × 0.5`，`need = 守军 + 1`                  | 刚好够用最好，别拿 100 军去打空地            |
| 串联抑制            | `-50`（目标格本 tick 刚被移动过）                       | 扩张时不要把 4 步全给同一支部队              |

**目标项刻意做成"只奖不罚"**：`dGoT < dGoF` 才加分，走远不扣分。早期版本用对称差值，结果是有目标时全图都往目标方向挤、背面的领土停止扩张；改成单向奖励后，矛头依然形成，但其他方向照常铺开。

### 3.2 增援（目标是己方格）

增援只在两种情形下得分：

- **向目标输血**：`dGoal` 变小，且 `goalW > 0`。分值 `15 + (dGoF - dGoT) × 12 + 兵力偏好`，低于任何合法占领分（基础 100），所以有地可占时一定先占。
- **紧急回防**：守家模式下走回自家将军，`8000 + n × 6`，压过一切。

无目标时，只有"向外"（`dMe` 变大）的增援得 `8 + 10 × Δ + 兵力偏好`，用来把纵深里的存量军队往前线推。

**队友格永远不进入**：规则规定增援不改变归属，把军队送进队友格子等于白送。组队模式下队友被视为"不可攻击、不可捐赠"的存在。

### 3.3 `half` 的选择

```
从自家将军出发        → 能半量过半量，否则全量（将军永远留一半）
朝目标推进 / 高价值格  → 全量（矛头不衰减）
其余能半量解决        → 半量（保留纵深）
半量不够              → 全量
```

### 3.4 影子结算

每执行一条指令，就在本地的 `arm` / `own` 副本上按规则第 4~6 条结算一次，并把新占的格子追加进 `myCells`。这样后面 3 条指令看到的是"前一条已经生效"的状态，从而支持**同一 tick 内把一支部队串联推进最多 4 格**——这是打城和斩首时把兵力快速送到墙根的关键。

影子结算与真实结算只有一处偏差：攻陷敌方将军时，真实规则会把对方**全部领土**转给进攻方且每格军队减半，影子模拟只改了将军格本身。由于每 tick 最多 4 条指令，这个偏差不会导致非法指令，只会让后续 1~3 条指令的收益估计偏保守。

## 4. 战术行为

### 4.1 扩张

没有目标时，唯一的驱动力是 `dMe` 梯度：每一格都往"离自家将军更远"的方向走。这等价于从将军向外做泛洪填充，四个方向同时推进。

`half` 的使用让每个格子保留一半驻军，形成一条有纵深的输送链；同时 `-50` 的串联惩罚让 4 条指令尽量落在 4 个不同格子，避免只推进一条线。

### 4.2 打城

中立城市 40~50 驻军且不增长，打下来后每 tick `+g` 永久产出。策略把"最近的非己方城市"设为目标，矛头自然指向它；打不动时（`k ≤ 守军`）该方向不生成指令，军队就在墙根自然堆积，等堆够了再一次性突破。

这里有一个自组织的效果：**打不动就自动攒兵**，不需要额外的"集结"状态机。

### 4.3 斩首

敌方将军一旦被目击，坐标写进 `memory.eg` 并永久保留。之后它就成为斩首候选，权重 `+60000` 保证只要打得下来就一定打。

打敌方将军的收益不只是 1500 分里的那一份：目标玩家的**全部领土**会转给进攻方（每格军队减半），这在"领土占比"计分下是一次巨大的跳变，通常直接决定胜负。

### 4.4 防守

- `threatNear > 将军驻军` → 切守家模式，全军回防，目标就是将军格。
- 将军是否允许向外派兵，由 `leaveGen = 将军驻军 ≥ 6 且 ≥ 2.2 × threatNear + 6` 控制。威胁越大，需要留在将军身上的兵越多。
- 从将军出发永远用 `half`，绝不把将军抽空。

### 4.5 迷雾信息利用

- **结构信息**（山地、城市、将军位置）直接读 `terrain`，服务器帮忙记着。
- **动态信息**（`owner`、`army`）只在可见时有效，且因为 §1.1 的推论，所有"要打的格子"都是可见的，所以决策用到的数值全部精确。
- **跨 tick 信息**只有一项：敌方将军的最后目击位置。其余一概不记——见 §5 的理由。

## 5. 状态记忆

`memory` 的结构只有一层：

```js
{
  v: 2,                                  // 版本号，用于识别/丢弃不兼容的旧记忆
  eg: {                                  // enemy generals
    3: [x, y, seenTick, seenArmy],       // 玩家 id → 最后目击信息
    7: [x, y, seenTick, seenArmy]
  }
}
```

### 更新规则

- **写入**：某个可见格 `terrain === 3`、归属是敌人且不是队友 → 覆盖该玩家的记录。
- **删除**：
  - 该玩家已出局（`players[p].alive === false`）；
  - 该玩家成了队友；
  - 记录的格子当前可见，但归属不再是该玩家，或地形不再是将军。

### 为什么只记这一项

1. `terrain` 免费且永久，地图不需要自己存。
2. 动态信息（`owner`/`army`）在视野外**本来就不该被相信**，记下来只会让决策基于过期数据。
3. 返回值有 32 768 字符上限，且**格式非法会直接判负出局**。记忆越复杂，序列化失败或结构损坏的风险越高。当前实现在最坏情况（16 名敌人全部被目击）下也只有几百字节。
4. 记忆越小，跨局复现越容易对齐。

### 容错

`memory` 会被当作**不可信输入**处理：非对象、`v` 不匹配、`eg` 不是对象、记录是 `null`、坐标越界、键名不是数字——全部走"重建"或"删除该条"的分支，不会抛异常。这一点在本地测过（见 §10）。

此外 `decide` 外层包了一个 `try/catch`。协议规定"执行异常立即出局"，所以把未预料的异常降级为"本 tick 待命 + 重置记忆"，比直接判负严格更好。正常路径不会走到这个分支，它对性能没有可测影响。

## 6. 复杂度

记 `N = W × H`（最大 `168 × 164 = 27 552`），`M` 为己方格子数，`K` 为已目击的敌方将军数（≤ 15）。

| 阶段         | 时间                    | 说明                           |
| ------------ | ----------------------- | ------------------------------ |
| 展平         | `O(N)`                  | 3 个 typed array               |
| 将军记忆扫描 | `O(N + K)`              | 一次全图 + 遍历 `eg`           |
| `BFS(dMe)`   | `O(N)`                  | 每格最多入队一次               |
| 威胁评估     | `O(N)`                  |                                |
| 城市扫描     | `O(N)`                  |                                |
| `BFS(dGoal)` | `O(N)`                  | 目标是将军时复用 `dMe`，省一次 |
| 贪心选步     | `O(4 × M × 4)` ≤ `O(N)` | 4 轮 × 己方格 × 4 方向         |

**总时间 `O(N)`，总空间 `O(N)`**（4 个地图 typed array + 1 个 BFS 队列 + 最多 2 个距离场），外加 `O(K)` 的记忆。

没有递归、没有动态分配的大对象、没有正则、没有字符串拼接在热路径上。BFS 队列预分配为长度 `N` 的 `Int32Array`，因为每格最多入队一次，不会溢出。

## 7. 确定性与可复现性

- **不读任何非确定性输入**：没有 `Date`、`performance`、`Math.random`、`crypto`，也不依赖对象键的插入顺序做决策。
- **不依赖顶层可变状态**：`strategy.js` 的顶层只有常量。所有跨 tick 状态都走 `memory`，所以即使 Worker 被重建、或同一份代码在一局中途被替换实例，行为也不会漂移。
- **平局有确定的裁决**：打分用严格大于比较（`sc > bestSc`），因此同分时**先遍历到的候选胜出**。遍历顺序完全固定——`myCells` 按格子索引升序（行优先），方向按 `上、右、下、左` 固定顺序。
- **浮点使用受限**：分数用 `double` 计算，但参与运算的量都是小整数或 `.5` / `.8` 这类可精确表示的常数，不会出现累积误差导致的顺序翻转。所有输出的数字都是整数或布尔值。

结论：**同一地图种子 + 同一对手名单 + 同一份代码 ⇒ 完全相同的对局**。

## 8. 局限

诚实地列出这套策略做不到的事：

1. **单目标聚焦**。一次只朝一个目标推。如果同时被两个方向夹击，只能顾一头。
2. **没有对手建模**。不记录"哪个方向出现过谁""上次被谁偷家"，也不区分对手是激进型还是龟缩型。所有决策只依赖当前可见状态 + 敌方将军位置。
3. **迷雾区只有结构记忆，没有兵力估计**。对视野外的敌军集结没有概率模型，推进时可能一头撞进更大的预备队。§1.1 保证了"不会打输还硬上"，但保证不了"不会走进包围圈"。
4. **不评估"守不守得住"**。占领后不预留防守预算。对手下一 tick 用更大兵力反打，格子就会丢。策略里没有"这个格子值不值得守"的判断。
5. **城市价值是常数**。`+900` 不随剩余 tick 折现。理论上在 `maxTicks` 前 10 tick 刚打下的城市回报很低，策略仍会去打。
6. **终局不切换策略**。接近 `maxTicks` 时没有从"扩张"切到"保军力 / 保领土"。规则里平局按总军力判胜，理论上终局应该收缩战线、囤积兵力。
7. **不做多 tick 规划**。每 tick 独立贪心，可能在山口、桥梁这类瓶颈地形反复拉锯，也可能为了一个 3 格外的目标绕远路。
8. **组队模式不主动协防**。队友只被当作"不可攻击、不可捐赠"的存在，不会主动把兵送到队友将军旁边救火。
9. **不做欺骗**。没有佯攻、没有假装薄弱引诱对手深入。

## 9. 设计取舍

### 9.1 精确战斗判定 vs 试探性进攻 → 选精确

规则是"输的一方全灭，赢的一方保留差额"。这意味着打不赢的仗是**纯亏**，没有任何"消耗对手"的补偿（对手反而净赚）。所以策略把 `k ≤ 守军` 做成硬约束，永不进攻。

代价：放弃了用少量军队骚扰、拖慢对手节奏的价值。在"军力占比"计分下，这个代价是真实存在的——但换来的是**零无谓损失**，长期看更划算。

### 9.2 `half` vs 全量 → 按用途分流

`half` 保留纵深但几何衰减，全量一步只损 1 但抽空后方。策略不选边，而是按"这一步是不是在朝目标推进"分流：推进用全量，铺地用半量，将军出发永远半量。这样矛头不衰减，同时后方不至于全是 1 军空格。

### 9.3 单目标 vs 多目标 → 选单目标 + 距离衰减

4 步/tick 的预算下，多目标会让每一路都凑不出能突破的兵力。所以选一个主目标，并用 `goalW = max(0, 48 - 4·dGoF)` 让目标拉力**只在目标附近生效**，远处仍按纯扩张处理。这样"聚焦"和"铺开"不冲突。

### 9.4 记忆极小 vs 记更多 → 选极小

`terrain` 免费、动态信息不可信、输出有 32KB 上限且格式非法直接出局。三个理由叠加，记更多的期望收益为负。所以只记敌方将军。

### 9.5 贪心 vs 搜索 → 选贪心

200ms 内做不出有意义的博弈树（对手是同时决策的，本就没有完美的搜索框架）。贪心 `O(N)`、行为可预测、完全可复现，而且在"每 tick 只有 4 步、状态连续变化"的场景里，贪心的边际损失很小。

### 9.6 影子模拟 vs 无状态选步 → 选影子模拟

没有影子模拟，4 条指令会各自基于 tick 开始的状态独立打分，无法串联推进，打城和斩首会慢 3~4 倍。代价是与真实结算在"击杀将军后领土转移"上有偏差，但这个偏差只影响估计、不影响合法性。

### 9.7 不追求"每 tick 都动"

`moves` 为空是合法的。当所有合法进攻都打不赢、所有增援都不划算时，策略会返回空数组待命——攒兵比乱动好。

## 10. 本地验证

**以下数字全部来自我自己按规则文本写的最小复现器（Node.js），不是官方引擎的评测结果。** 复现器实现了：视野 8 邻域、迷雾记忆、4 条指令顺序结算、轮转先手、战斗与将军易主、产量公式、结束判定。它可能在细节上与官方实现有差异，因此下面的数字只能用来判断**量级和行为倾向**，不能当作比赛成绩。

跑过的检查：


1. **协议合法性**：`moves` 是数组、长度 ≤ 4、`from` 是整数坐标且在界内、`dir` 在四个合法值内、`half` 是布尔、`JSON.stringify` 后远小于 32 768 字符。2 人图与 4 人图共 4 局、约 3.6 万条指令，**协议违规 0 次**。
2. **健壮性**：`memory` 为 `null` / 字符串 / `{}` / `v` 不匹配 / `eg` 里塞 `null`、越界坐标、非数字键 —— 均正常返回，不抛异常。`you.alive === false` 返回空 `moves`。将军在角落、全图迷雾且将军仅 1 军（无处可走）也能正常处理。
3. **确定性**：同一 observation 连续调用两次，输出逐字节一致。
4. **记忆不膨胀**：连续 300 tick，`memory` 序列化长度恒为 15 字节。
5. **耗时量级**（自建复现器，Node.js 22，单线程）：
   | 地图                             | 格数   | 己方格数 | 单次 `decide` |
   | -------------------------------- | ------ | -------- | ------------- |

   | 辽阔 16 人（人为造出的极端局面） | 27 552 | 9 385    | ≈ 36 ms       |
   最后一行是刻意构造的病态场景（一个玩家占了全图 34%、且每格都有 3 以上军队），实际对局中单个玩家的领土通常只有 1 700~2 000 格，对应十几毫秒。相对 200 ms 预算有 5 倍以上余量。
6. **行为倾向**（4 人标准图，4 个玩家跑同一份代码）：
   | 指标         | 观察值               |
